# Design

A VS Code for Web extension that compiles, runs and debugs C/C++ entirely in the browser using
`clang.wasm`/`lld.wasm` (built by the `llvm-project` fork) and an lldb-derived symbol/value library.
Output is always WebAssembly (WASI); only minor restrictions are placed on compiler flags.

## Layout
```
src/web/
  extension.ts                 # activation, command registration
  buildWorkspace.ts            # workspace build orchestration, artifact dir choice
  projectConfig.ts             # settings, tasks.json and launch.json read from VS Code
  runProgram.ts
  tasks.ts
  clangd/                      # language client and index sweep
  debug/                       # inline DAP adapter, stub channel, lldb reactor host
  toolchain/                   # vscode-free logic plus the compiler host (toolchain.ts)
  test/suite/                  # *.node.test.ts run in node, the rest under test-web
documents/
scripts/                       # toolchain dist and test runner scripts
```
Reusable helpers are listed in `documents/helpers.md`.

## Components
- `src/web/extension.ts`: activation; registers the build command, debug configuration provider and inline debug adapter factory.
- `src/web/toolchain/toolchainDownload.ts` (vscode-free, node-tested) and `toolchainStore.ts` (extension-storage cache, progress UI): the toolchain loader; see Distribution.
- `src/web/toolchain/toolchain.ts`: `build(request)` is the single boundary between VS Code UX and the compiler host. The host (Workers, WASI, spawn hook, threads) sits behind it so UX layers never touch wasm details.
- `src/web/debug/`: the debugger. `debugController.ts` holds the Debug Adapter Protocol logic and is vscode-free; it reaches the program only through the `DebuggeeSession` interface (`debuggeeSession.ts`), implemented today by `stubDebuggee.ts` over the in-process stub's stdio channel (see Debug stub channel) and later by the custom runner. `debugAdapter.ts` is the inline adapter shell (web extensions cannot spawn processes): it builds in debug mode, runs the program under `wasm-wasi-core` and hosts the lldb reactor (`reactorHost.ts`). Debugging uses compile-time instrumentation plus lldb as a library (the reactor decodes DWARF and values; `wasmScan.ts` maps coverage guards to pcs and frame-base locals), not a live attach; rationale in the llvm-project fork's `documents/design.md` ("Debugging design"). `dwarfLines.ts` and `breakpointIndex.ts` turn a source line into the guards that stop there, because the reactor can map a pc to a line but not back; `pathMapper.ts` maps the client's source paths to `/workspace`.
- `src/web/clangd/clangdClient.ts`: starts clangd.wasm (downloaded from the toolchain manifest like clang.wasm/lld.wasm) as a long-lived `wasm-wasi-core` process on activation and feeds it to `vscode-languageclient/browser`'s `LanguageClient`, via a `MessageTransports` adapter over the process's pipe stdio (no Worker involved, unlike that package's usual browser setup). Files with no `compile_commands.json`/`compile_flags.txt` entry get the build's compile flags plus `vscwclang.flags` through clangd's `fallbackFlags` initialization option (`fallbackFlags.ts`), so the wasm sysroot and libc++ headers resolve; clangd itself has no `-extra-arg` option. See "Scope" below and documents/remaining_work.md "V3 idea: clangd".
- `src/web/clangd/indexSweep.ts` (`IndexSweep`): drives clangd's fake background indexing (`didOpen`/`didClose` per workspace file, since the single-threaded build has no indexer thread), wired through `LanguageClientOptions.middleware.didOpen` so a real editor open always closes any fake copy first. Files drain in three tiers: those named by the default build task or `launch.json` configurations (`configuredSources`), then files sharing a folder with an open editor, then the rest. Progress shows in a status bar item, and `vscwclang.indexing.enabled`/`pauseMs`/`holdOpenMs` toggle and pace it; see remaining_work.md "Chosen indexing mitigation".
- Binaries (`clang.wasm`, `lld.wasm`, `lldb-wasm-reactor.wasm`, plus a sysroot tree; the `lldb.wasm` CLI is not needed, because the debugger uses lldb only as a library through the reactor's exports, never the lldb/lldb-dap command interpreter) are built by the llvm-project fork (release tree `release/llvmorg-24.0.0-git-wasi.2`: `bin/`, `sysroot/`, `resource/`, `compile-flags.json`, `MANIFEST`) and are not in the .vsix. A local copy lives under `llvm-artifacts/` (gitignored) for development; see Distribution.

## Contract with the toolchain
The authoritative host contract (spawn hook, wasi-threads, Worker termination and cleanup) is `documents/js-host-contract.md` in the `llvm-project` fork. This extension is the real browser host that contract describes.

## Distribution
The core extension is small and ships no toolchain. On first use it downloads zips of the toolchain (clang + lld, sysroot + resource dir, later lldb) from a host that sends `Access-Control-Allow-Origin` and `Cross-Origin-Resource-Policy: cross-origin`, as vscode.dev is `COEP: require-corp`. `raw.githubusercontent.com`, jsDelivr and unpkg do; GitHub *release assets* do not. Each zip is unzipped in the extension host (`fflate`), verified against SHA-256 hashes embedded in the core extension (which replace Marketplace signing for these files), and cached in extension storage. Files over the host's per-file cap are split into chunks (`scripts/split-wasm.mjs`, `src/web/toolchain/chunkedFile.ts`) and reassembled before compiling. `WebAssembly.compile` then runs on the unzipped bytes and `wasm-wasi-core` executes them; this path (unzip, compile, run `clang --version`) is verified. The sysroot is unzipped into a `wasm-wasi-core` memory file system mounted read-only at `/sysroot`; flags come from the release's `compile-flags.json`. 
The loader (`toolchainDownload.ts`, `toolchainStore.ts`): the extension pins one SHA-256, of the toolchain's `manifest.json` (`toolchainPin.ts`, written by `scripts/make-toolchain-dist.mjs --pin`). The manifest lists each file's final size and hash plus its payload chunks (each with its own size and hash; `clang.wasm`/`lld.wasm` payloads are zips, `sysroot.zip` and `compile-flags.json` are raw). Chunks download four at a time with retries (not on 4xx other than 408/429), each verified before use; the result is unzipped, checked against the file hash, and only then written to `globalStorageUri/toolchain/<manifest hash>/`. A cached file is trusted only if its size and hash match, so an interrupted download resumes per file and a pinned toolchain works offline. Other cached versions are deleted after a successful download. One notification shows progress for everything still missing (cancellable; completed files are kept). The sysroot stays cached as its zip; unzipping into the memory file system happens once per session. The application-scoped setting `vscwclang.toolchainUrl` replaces the host and skips the pin (development; a workspace cannot set application-scoped settings), and is how tests and local runs use `llvm-artifacts/dist`. If the pinned hash is ever empty, `build()` fails with a message that says so.

Hosting layout: the unchunked, generic artifacts (`clang.wasm`, `lld.wasm`, `lldb.wasm`, reactor, sysroot) are GitHub releases of the `Ambeco/llvm-project` fork, the source of truth. What the extension downloads is served from a separate public repo (`Ambeco/llvm-artifacts`, files under `dist/`): the chunked/zipped copies produced by `scripts/split-wasm.mjs` / `scripts/zip-wasm.mjs`, `compile-flags.json`, and a manifest with SHA-256 hashes, fetched through jsDelivr or raw.githubusercontent.com at an immutable tag per toolchain version (e.g. `https://cdn.jsdelivr.net/gh/Ambeco/llvm-artifacts@v24.0.0/dist/...`). The extension pins the tag, so a toolchain change ships as an extension update. The toolchain repo is kept small by publishing each version as an orphan commit (or force-pushing a branch), never accumulating history; chunks stay at 16 MiB, well under per-file caps. Only extension-specific files (`compile-flags.json`, manifest) belong to this layout; this extension repo holds no binaries.

## Host
V1 uses `wasm-wasi-core` (a separate VS Code extension; it requires `SharedArrayBuffer`, available on vscode.dev) to run a single-process, single-thread `clang.wasm` (cc1 in-process) and `lld.wasm`, orchestrated by the extension. `toolchain.build()` compiles each source with `clang++`/`clang` (`-c -o -`: clang writes each object to stdout, the host puts it in an in-memory file system mounted read-only at `/obj` for `wasm-ld`, so only the final `.wasm` is written to the workspace), keeps going after a failed compile so all diagnostics are reported, then links with `wasm-ld`. User flags are checked first by `flagPolicy.ts` (rejections carry did-you-mean text); clang/wasm-ld text output is parsed by `diagnostics.ts` and published by `diagnosticsCollection.ts`: the Problems panel is cleared when a build starts and refreshed after each source compiles (`BuildRequest.onDiagnostics`), so errors appear before later files finish; the final publish from the finished result is authoritative. Compiled `clang.wasm`/`lld.wasm` modules and the unzipped sysroot are cached in memory across builds. `wasm-wasi-core` cannot host the spawn hook: it never exposes the `WebAssembly.Instance` or custom imports. Concurrent per-file compiles, spawned cc1/wasm-ld and in-module threads therefore need V2, our own Worker host following `js-host-contract.md`. User programs can still be run under `wasm-wasi-core`.

The `wasm-wasi-core` host is deliberately a thin first slice. The extension stays minimal (build, run, clangd, the DAP basics) and the next major step is V2, our own Worker host. V2 is what unlocks threads, the spawn hook, concurrent compiles, trap and uncaught-exception reporting (no `run()` hang) and full debugging (pause and breakpoint changes while the program runs, traps as stopped states). Work that only compensates for `wasm-wasi-core`'s limits (the debug stub's stdio channel, trap-hang workarounds) is therefore kept small.

## Flags, run and tasks
`request.flags` is one list; `splitFlags` (flagPolicy.ts) routes `-l`, `-L` (relative dirs resolved under `/workspace`) and `-Wl,a,b` (split into separate args) to wasm-ld, everything else to `clang -c`. `vscwclang.run` (`runProgram.ts`) builds, then runs the .wasm under `wasm-wasi-core` with `createPseudoterminal()` as stdin/stdout/stderr: stdin is the terminal's line mode (echo, line editing, one line per Enter, no EOF key); Ctrl+C or closing the terminal terminates the process. `tasks.ts` provides `vscwclang` build tasks as `CustomExecution` that print clang's text; the `$vscwclang` matcher turns `/workspace/<file>:l:c: error|warning:` lines into Problems (notes and linker lines are not matched).

## Scope
North star: compile, run and debug self-contained C/C++ programs (and a library's tests) in a browser tab with nothing installed, on machines where installing a compiler is impossible or unwanted (Chromebooks, locked-down school or work machines, tablets, `github.dev`/`vscode.dev` on a repo with no cloud VM). Non-goals: a POSIX userland (shell, coreutils), networking, GUI and native-library linking, MSVC project formats, replacing desktop toolchains. Before adding a feature, check it serves the north star; most "it would be cool if programs could ..." ideas below it belong in a later, separate project.

Framed against the desktop C/C++ (cpptools) extension this project is meant to replace entirely in the browser, cpptools plays three roles, and this extension's scope maps one-to-one:
1. **Build**, reading `tasks.json`'s default build task (`g++`/`clang++`-style) — done (design.md "Project model and integration").
2. **Debug**, reading `launch.json` (`cppdbg`/`cppvsdbg`) and implementing the Debug Adapter Protocol (a `DebugAdapterDescriptorFactory`/inline adapter registered for a debug type) — `args`/`preLaunchTask` are read for Run today, but the DAP adapter itself (breakpoints, stepping) is not implemented; see Milestones 4-6.
3. **IntelliSense** (completion, hover, go-to-definition, diagnostics-as-you-type), via VS Code's ordinary language-provider APIs — a minimal `clangd` language client is wired up (`src/web/clangd/clangdClient.ts`, Milestone 3); the fake-indexing sweep (with progress and settings) is in place, most polish is not (documents/remaining_work.md "V3 idea: clangd").

CMake (and Make/Bazel/Meson) support is explicitly not this extension's job to reimplement: **Plan A (decided)** is a separate extension that drives those build systems and feeds this one (and clangd, once it exists) through the neutral `compile_commands.json` format this extension already reads — see "Project model and integration" below. **Plan B (fallback only, not started)** is implementing a reasonable CMake subset directly in this extension if a separate extension proves impractical (e.g. no wasm `cmake`/`make` binary materializes). Do not start Plan B work without re-confirming Plan A is blocked.

## cpptools settings compatibility
Where a setting has a cpptools (`C_Cpp.*`) equivalent we mirror its name and shape, and read the cpptools value as a fallback, so a project configured on desktop works here unchanged. VS Code returns settings.json values for unregistered keys, and cpptools has no web build, so `C_Cpp.*` is read straight from `getConfiguration('C_Cpp')` (`projectConfig.ts`: `userFlags`, `loggingLevel`, `intelliSenseEnabled`; `isUserSet` uses `inspect()` to tell a user value from our default). Mapping is vscode-free in `toolchain/cppToolsSettings.ts`:
- Variables in settings: `vscwclang.flags`, `run.args`, `run.env` values and the `C_Cpp.default.*` flag entries go through `projectModel.resolveVariables` (`projectConfig.ts` `resolveSettingStrings`), the same expansion `tasks.json`/`launch.json` get: `${workspaceFolder}` (and `${workspaceRoot}`, `${cwd}`) is `/workspace`, because the compiler and program see guest paths. An unsupported one (`${env:}`, `${command:}`, `${file}` with no editor) throws naming the setting and entry, except for clangd's startup flags (`userFlags(log, true)`, no active file) and `C_Cpp` entries, which are dropped with a note. Host-relative globs and paths (`sourceGlobs`, `compileCommands(.include)`, `files.exclude` keys) just drop a leading `${workspaceFolder}/` (`stripWorkspaceFolder`).
- `vscwclang.flags`, when the user has not set it, becomes its default plus flags from `C_Cpp.default.defines`, `includePath` (workspace paths only; `${workspaceFolder}` becomes `/workspace`, `/**` is read as the directory), `cppStandard` (`c++NN`/`gnu++NN`), `cStandard` (`cNN`/`gnuNN`) and `compilerArgs`. The two standards apply only to sources of their own language (`BuildRequest.languageFlags`, placed before `flags` so a user `-std=` wins); clangd's single fallback flag list ignores them. Setting `vscwclang.flags` explicitly replaces this entirely, as does `vscwclang.useCppToolsSettings: false`. Unmappable entries are dropped with a did-you-mean line in the output channel. Build and the clangd `fallbackFlags` share `userFlags`.
- `vscwclang.files.exclude` (replaces the old directory-name list `sourceExclude`) is a glob object like `C_Cpp.files.exclude`, which is merged in (the setting the user actually set wins a conflict; `false` un-excludes). `toolchain/sourceFilter.ts` `makeSourceExcluder` supports `**`, `*`, `?`, `{a,b}`, ignores case, anchors globs without `**` at the workspace folder, and excludes a path when its own glob or any ancestor folder matches; `when` objects are ignored. Build and the index sweep share it (`projectConfig.ts` `sourceExcluder`); files named explicitly by a task or database are never excluded.
- `vscwclang.compileCommands` is string or array like `C_Cpp.default.compileCommands` (first non-empty entry used, `${workspaceFolder}/` stripped), falling back to that setting.
- `vscwclang.loggingLevel` (None/Error/Warning/Information/Debug, default `C_Cpp.loggingLevel`) picks clangd's `-log=` level (error/info/verbose) and whether clangd's stderr is echoed to the output channel.
- `vscwclang.intelliSense.enabled` (default off when `C_Cpp.intelliSenseEngine` is `disabled`) skips starting clangd. Both it and `loggingLevel` need a window reload.

## Run environment
User programs run under `wasm-wasi-core` (WASI preview 1). A program sees only what is mounted: the workspace at `/workspace`; writable `/tmp` (emptied before each run) and `/home/user` (kept), both `vscodeFileSystem` mounts of directories in extension storage; there is no `/etc` or `/dev`. The environment is `HOME=/home/user`, `TMPDIR=/tmp`, `USER=user`, `LANG=C.UTF-8` plus `vscwclang.run.env` (`null` removes a default). WASI has no cwd, so a constructor in the helper object linked into every program (`ABORT_SHIM_SOURCE`) calls `chdir("/workspace")`, making relative paths resolve there. Arguments come from `vscwclang.run.args`, or from the prompt of `vscwclang.runWithArgs` (shell-style quoting, `splitArgs`; last answer kept in workspace state). Sockets are stubbed (`sock_*` return not-implemented; preview 1 has no `connect`), and there are no processes or signals. Mount kinds available: workspace folder, any VS Code file system (writable), extension files, and an in-memory file system (read-only to the guest). Terminal input is wasm-wasi-core's line mode: `handleInput` takes one key per call (a multi-character chunk is inserted as text), and a line typed before the program reads is returned without its `
` unless `runProgram` patches `readline` (`terminateTypedAheadLines`).

Library-level behavior (wasi-libc, verified by building and running under Node WASI): `fork` and `popen` are undeclared, so using them is a compile error; `system()` is declared but undefined, so it is a link error (`undefined symbol: system`); `msync` is a link error; `mmap` needs `-D_WASI_EMULATED_MMAN` and `-lwasi-emulated-mman` and only emulates reading (file contents are copied into memory): a write through a `MAP_SHARED` mapping is silently NOT written back to the file. `fopen("/tmp/...")` works through the `/tmp` mount. A failed `assert`, `abort()` or `std::terminate` exits 134 through a weak `abort()` helper linked into every program, since a trap would hang `run()`.

## Build artifacts
Objects live in memory only. The linked `.wasm` and `build.log` go where the user can reach them (`chooseArtifactDir` in `buildWorkspace.ts`; the policy is in `artifactPolicy.ts`: `isWritableFileSystem(scheme)` is not false and the scheme is not a virtual-repo one; an unknown writability is tried and falls back on failure). When the output is outside the workspace it is a `vscodeFileSystem` mount at `/out` for wasm-ld; an explicit task `output` stays workspace-relative. For local, writable folders: inside the folder (under `.vscwclang/<mode>/`, so debug and release builds from two tabs or two synced devices do not collide); this also lets a synced folder share them across devices. For read-only or virtual folders (`vscode-vfs://` repos, where a written file would also show up as a pending change in Source Control) they go in extension storage instead, which lets read-only repositories build and run. A task's `output` overrides the location; a dedicated setting is not provided. Caches shared between devices must be content-addressed (hash of source, flags and toolchain) so concurrent writers cannot clash.

## Project model and integration
Goal: a desktop VS Code project that builds with clang should build, run and debug the same here. `toolchain.build(request)` (sources, flags, output, mode) stays the only boundary to the compiler; a "project model" step in front of it turns what the workspace already contains into that request. This extension owns the clang-compatible inputs desktop VS Code uses: `tasks.json` (tasks that call `g++`/`clang++`, mapped through `flagPolicy`) and `launch.json` (`program`, `args`). Solution and project files (`.sln`, `.vcxproj`) are out of scope because they almost always target non-clang compilers and flags.

`toolchain/projectModel.ts` (vscode-free, node-tested) does the mapping; `projectConfig.ts` reads the configuration through `workspace.getConfiguration('tasks' | 'launch', folder)` (never by parsing the files, which are JSONC). Variables resolve straight to guest paths (`${fileDirname}` is `/workspace/src`), so mapped flags are already valid for the compiler; unsupported variables, other compilers and unmappable arguments throw with a did-you-mean. `${file}` means the last C/C++ editor (`trackActiveCppFile`), since a focused terminal has no active editor. A task's flags replace `vscwclang.flags` and its sources replace `sourceGlobs`; the task's `-o` only names the `.wasm` (stem plus `.wasm`), which goes where the artifact policy says, so read-only folders still work and Run always runs what it built (`launch.program` is only used to find the task whose `-o` matches). `-g` selects debug mode. Dropped with a logged note: colour flags (they would put ANSI codes in the text the problem matcher parses), `-pthread`, `-static`, `-lstdc++`, `-m64`, `-mwindows`.

Which task and arguments apply: Build uses the default build task if it runs a g++/clang++-style compiler (a default task running `make` or `cl.exe` is skipped with a log line; a compiler task that cannot be mapped is an error), else the `vscwclang` settings. Run picks a `launch.json` configuration of a C/C++ debugger type (QuickPick when several, last choice first), then the build task from its `preLaunchTask`, else the task whose `-o` matches `program`, else the default build task, else the settings. Launch `args` (when the key exists) win over `vscwclang.run.args`; the explicit "with Arguments" prompt is pre-filled from them. Tasks of type `cppbuild` are also resolved by the task provider (so the Tasks menu runs them); `shell` tasks cannot be intercepted by a provider and are mapped only by the Build and Run commands. Launch `cwd` and `environment` are not applied.

Other build systems (Make, CMake, Bazel, Meson) belong in separate extensions, which cannot run `make`/`cmake` as native processes on the web anyway. They integrate through `compile_commands.json`, the neutral compilation-database format (`directory`, `command` or `arguments`, `file` per translation unit) already read by clangd and cpptools: this extension reads it as one more source of build plans, so any tool that emits it works with no code dependency. A versioned exported API (like the Git extension's `getAPI(1)`) and a command accepting a plain-data build request are the tighter options if needed later; the `vscwclang` task type is already a declarative form of the same request.

`compile_commands.json` is the third build source: Build and Run use the default `tasks.json` build task if it maps, else the database (`vscwclang.compileCommands`, else `compile_commands.json` or `build/compile_commands.json`), else `compile_flags.txt` (flags for every source, which still come from `sourceGlobs`), else the settings. The C/C++ extension only uses the database for IntelliSense, so build behavior follows CMake Tools instead: each source is compiled with the flags of its own entry (`BuildRequest.sourceFlags`; `-l`/`-L`/`-Wl,` flags found there are merged into the one link), and a database that names several CMake targets (object paths under `CMakeFiles/<target>.dir/`) shows a picker like CMake Tools' build target, last choice first, with "all targets" as an item. A database without targets (Bear, Make) links every entry; `vscwclang.compileCommands.include` globs narrow that. Entries are mapped by `planFromCompileCommands` with the same argument handling as tasks, minus the database's own mechanics (`-c`, `-o`, `-MD`/`-MF`/`-MT`, `ccache`/`sccache`/`distcc` wrappers); a second entry for a file, non-C/C++ files and entries outside the workspace are skipped with a logged note, and response files (`@x.rsp`) are errors. Databases are usually generated elsewhere, so absolute paths are rebased: they map under the workspace folder if they lie in it, else `inferHostRoot` finds where the folder sat by matching the longest tail of a source path that exists here (Windows paths and drive-letter case are normalized). Include directories outside that root (`/usr/include`, vcpkg) are dropped with a note instead of failing, since the sysroot provides the standard library and the compile error then names the missing header. Other unmappable flags (`-march=native`, `--target`) are errors, as for tasks. The database is usually gitignored, so it is mostly useful for local folders, not `github.dev`.

## Debug stub channel
Debug builds link `src/web/debug/debugStub.c`, the program-side half of debugging, because `wasm-wasi-core` accepts no custom imports. It is the `__sanitizer_cov_trace_pc_guard` hook (exported by the linker so `scanProgram` finds the call sites), so the program imports only WASI functions. It keeps a shadow call stack of (guard, `__stack_pointer`) per instrumented frame, checks breakpoints by a bit in the guard word itself (no table lookup), and supports step into/over/out by comparing stack pointers. Stepping is per basic block; the adapter repeats until the source line changes.

The channel is the program's own stdio. At startup the stub sends `hello` and blocks in `fd_read` until the host releases it, so breakpoints are armed before any user code runs. Stub to host: frames `ESC _ vscw <text> ESC \` inside stderr (`stop`, `mem`, `memerr`, `error`); `FrameDemux` splits them from the program's own stderr at any chunk boundary and passes other escape sequences through. Host to stub: `vscw bp|mem|go|into|over|out` text lines on stdin, read one byte at a time so nothing meant for the program is consumed. The host writes commands only while the program is stopped and forwards typed program input only while it runs. Memory pages (4 KiB) are read by the stub itself (bounds-checked, so a wild address reports `memerr` instead of trapping).

What the debugger can and cannot do follows from where the hook sits. The coverage hook runs at the start of every basic block, so stops happen only there: a line breakpoint stops at the start of the block containing the line (the `setBreakpoints` response says so when that is an earlier line), and stepping moves block to block, repeating while the line and frame are unchanged. A stop at a function's entry block sees parameters before they are spilled to the stack. The Variables pane lists no locals, because the reactor cannot enumerate them; hover, Watch and the Debug Console evaluate variable paths (`x`, `p.y`, `arr[2]`). Pause and breakpoint changes while the program runs need a host whose `capabilities` allow them; the stub's do not, so changes are queued to the next stop and Pause fails with an explanation. The program's stdout and stderr go to the Debug Console and its stdin is not connected.

lldb reads memory synchronously but the channel is asynchronous, so `PagedMemory` serves the current stop from a page cache, recording misses; `evaluateWithMemory` fetches the missed pages and re-runs the lldb call. lldb formats a failed read into the value text instead of throwing and keeps that result for the stop, so each re-run must first call `ReactorHost.setStop` again with the same frames. Verified on `wasm-wasi-core` pipes (`debugStub.test.ts`) and in a worker harness with blocking stdin plus the real reactor (`stubChannel.node.test.ts`).

## Alternatives considered
### Reader thread inside the debug stub
- Pros: would apply breakpoint changes and pause while the program runs freely.
- Cons: `wasm-wasi-core` has no thread-spawn; stdin is shared with the program, so a reader would consume its input (the channel works only because commands and program input never overlap); does not reduce overhead, which comes from the per-basic-block hook.

### Write build artifacts only to extension storage
- Pros: never touches the user's folder; works for read-only repositories.
- Cons: the user cannot reach the binary or logs, and nothing is shared across devices; used only for read-only or virtual folders.

### Parse Visual Studio solution and project files
- Pros: opens existing Windows projects directly.
- Cons: they target MSVC (`/std:`, `/W4`, Windows APIs, 64-bit assumptions), so almost none would compile with clang for wasm32 anyway; a large parser for little gain.

### Make a dedicated build-system extension call this one through a hard dependency
- Pros: simplest for the other extension; typed calls.
- Cons: couples release cycles; every build tool must know this extension. A shared file format (`compile_commands.json`) needs no coupling and also serves clangd.

### Ship the toolchain in Marketplace tooling extensions
- Pros: Marketplace signing and versioning; files served by the workbench with no CORS concerns.
- Cons: Marketplace per-vsix and per-file size caps are undocumented (reported 20-25 MB; clang alone is 24 MB gzipped), so it could need ~7 extensions kept in version lockstep; needs a publisher account per extension set; programmatic install on vscode.dev is unverified.

### Serve the chunked toolchain from this extension repo
- Pros: one repo; no extra hosting setup.
- Cons: every toolchain version's chunks (~100+ MB each) stay in git history forever, bloating clones of the extension repo; mixing binary releases with extension source makes history and tags confusing.

### Download from GitHub release assets
- Pros: natural place to publish the fork's builds.
- Cons: `release-assets.githubusercontent.com` sends no CORS headers, so vscode.dev's COEP blocks the fetch.
### Bundle the wasm binaries in the .vsix
- Pros: works offline immediately; simple.
- Cons: ~380 MB (clang, lld, lldb, lldb reactor) exceeds practical extension size limits and slows every install/update.

### Use the browser's own debugger (CDP / DevTools DWARF extension)
- Pros: no instrumentation needed.
- Cons: unreachable from a web extension host (no `chrome.*`/CDP); settled "no" in the fork's notes.

### Run a wasm interpreter to control execution
- Pros: full step control.
- Cons: large correctness surface; much slower than V8's JIT.
