# Design

A VS Code for Web extension that compiles, runs and debugs C/C++ entirely in the browser using
`clang.wasm`/`lld.wasm` (built by the `llvm-project` fork) and an lldb-derived symbol/value library.
Output is always WebAssembly (WASI); only minor restrictions are placed on compiler flags.

## Layout
```
src/web/
  extension.ts                 # activation, command registration
  buildWorkspace.ts            # workspace build orchestration, artifact dir choice
  projectConfig.ts             # settings, tasks.json and launch.json read from VS Code
  runProgram.ts
  tasks.ts
  clangd/                      # language client, compile-command overlay for background indexing
  host/                        # Worker host (guest WASI, RPC channel, GuestProcess)
  debug/                       # inline DAP adapter, stub channel, lldb reactor host
  toolchain/                   # vscode-free logic plus the compiler host (toolchain.ts)
  test/suite/                  # *.node.test.ts run in node, the rest under test-web
documents/
scripts/                       # toolchain dist and test runner scripts
```
Reusable helpers are listed in `documents/helpers.md`.

## Components
- `src/web/extension.ts`: activation; registers the build command, debug configuration provider and inline debug adapter factory.
- `src/web/toolchain/toolchainDownload.ts` (vscode-free, node-tested) and `toolchainStore.ts` (extension-storage cache, progress UI): the toolchain loader; see Distribution.
- `src/web/toolchain/toolchain.ts`: `build(request)` is the single boundary between VS Code UX and the compiler host. The host (Workers, WASI, spawn hook, threads) sits behind it so UX layers never touch wasm details.
- `src/web/debug/`: the debugger. `debugController.ts` holds the Debug Adapter Protocol logic and is vscode-free; it reaches the program only through the `DebuggeeSession` interface (`debuggeeSession.ts`), implemented today by `stubDebuggee.ts` over the in-process stub's stdio channel (see Debug stub channel) and later by a runner that pauses through shared memory. `debugAdapter.ts` is the inline adapter shell (web extensions cannot spawn processes): it builds in debug mode, runs the program on the Worker host and hosts the lldb reactor (`reactorHost.ts`). Debugging uses compile-time instrumentation plus lldb as a library (the reactor decodes DWARF and values; `wasmScan.ts` maps coverage guards to pcs and frame-base locals), not a live attach; rationale in the llvm-project fork's `documents/design.md` ("Debugging design"). `dwarfLines.ts` and `breakpointIndex.ts` turn a source line into the guards that stop there, because the reactor can map a pc to a line but not back; `pathMapper.ts` maps the client's source paths to `/workspace`.
- `src/web/clangd/clangdClient.ts`: starts clangd.wasm (downloaded from the toolchain manifest like clang.wasm/lld.wasm) as a long-lived Worker-host process on activation and feeds it to `vscode-languageclient/browser`'s `LanguageClient`, via a `MessageTransports` adapter over the process's pipe stdio (not the Worker transport that package usually uses in the browser). Files with no `compile_commands.json`/`compile_flags.txt` entry get the build's compile flags plus `vscwclang.flags` through clangd's `fallbackFlags` initialization option (`fallbackFlags.ts`), so the wasm sysroot and libc++ headers resolve; clangd itself has no `-extra-arg` option. See "Scope" below and documents/remaining_work.md "V3 idea: clangd".
- `src/web/toolchain/toolchainFileSystem.ts`: read-only file system for the `vscwclang-toolchain:` scheme. clangd answers go-to-definition with guest-only `/sysroot` and `/resource` paths; `clangdClient.ts` maps them (and back) in its `uriConverters`, and the provider serves the unzipped `sysroot.zip` kept in memory by `loadSysroot`, so headers open read-only. Per-project settings are `"scope": "resource"` and read with the first folder's uri (`projectSettings`) so a folder's `.vscode/settings.json` applies in a multi-root workspace; the `C_Cpp.*` keys we read are contributed from package.json because workspace-level values of unregistered keys are dropped.
- `src/web/clangd/clangdConfig.ts` (vscode-free) and `compileOverlay.ts`: clangd runs as the wasi-threads build (`-background-index -j=N`, N from `navigator.hardwareConcurrency`, 2 to 4), so its parser pool and real background indexer run on Workers made by the extension host like any threaded tool. The indexer only knows files with compile commands: with no compilation database (`compile_commands.json` at the root or in `build/`, `vscwclang.compileCommands`, or `compile_flags.txt`) the extension sends the sources as `workspace/didChangeConfiguration` `compilationDatabaseChanges` (200 per message, `fallbackFlags` plus per-file flags) and sends created files as they appear. The sources are the files the `tasks.json` builds compile (`toolchain/indexTargets.ts`: every g++/clang++ and `vscwclang` task, its globs expanded like a build expands them, indexed with that task's own `-D`/`-I`/`-std`; the first task naming a file wins, and a task needing the editor, such as `${file}`, is skipped with a log note; a `tasks.json` change re-sends them). A `launch.json` configuration reaches the code only through its `preLaunchTask`, which is already one of those tasks. Files no task builds are not background-indexed (they are still parsed when opened); with no buildable task at all, every workspace source (`sourceGlobs` minus `files.exclude` and detected CMake/Ninja output folders) is indexed on fallback flags; with a database, clangd's own entries drive indexing and overlay commands would shadow them. Shards persist in a per-workspace folder of extension storage (hash of the folder URI, so projects with the same relative paths do not share shards), mounted at `/cache` (`XDG_CACHE_HOME`) and, with a database, also over `<database dir>/.cache/clangd`, where clangd insists on writing them (`shardMountPoint`); the longest mount wins, so the user's folder is never written and a read-only folder works. Progress is clangd's own work-done progress; there is no indexing setting or status item.
- Binaries (`clang.wasm`, `lld.wasm`, `lldb-wasm-reactor.wasm`, plus a sysroot tree; the `lldb.wasm` CLI is not needed, because the debugger uses lldb only as a library through the reactor's exports, never the lldb/lldb-dap command interpreter) are built by the llvm-project fork (release tree `release/llvmorg-24.0.0-git-wasi.2`: `bin/`, `sysroot/`, `resource/`, `compile-flags.json`, `MANIFEST`) and are not in the .vsix. A local copy lives under `llvm-artifacts/` (gitignored) for development; see Distribution.

## Contract with the toolchain
The authoritative host contract (spawn hook, wasi-threads, Worker termination and cleanup) is `documents/js-host-contract.md` in the `llvm-project` fork. This extension is the real browser host that contract describes.

## Distribution
The core extension is small and ships no toolchain. On first use it downloads zips of the toolchain (clang + lld, sysroot + resource dir, later lldb) from a host that sends `Access-Control-Allow-Origin` and `Cross-Origin-Resource-Policy: cross-origin`, as vscode.dev is `COEP: require-corp`. `raw.githubusercontent.com`, jsDelivr and unpkg do; GitHub *release assets* do not. Each zip is unzipped in the extension host (`fflate`), verified against SHA-256 hashes embedded in the core extension (which replace Marketplace signing for these files), and cached in extension storage. Files over the host's per-file cap are split into chunks (`scripts/split-wasm.mjs`, `src/web/toolchain/chunkedFile.ts`) and reassembled before compiling. `WebAssembly.compile` then runs on the unzipped bytes and the Worker host executes them. The sysroot is unzipped into in-memory file systems (`MemoryGuestFs`) mounted read-only at `/sysroot` and `/resource`; flags come from the release's `compile-flags.json`. 

The extension activates on startup (`onStartupFinished`) and starts clangd and the toolchain prefetch as soon as the workspace has C/C++ files (a document, or `findFiles`; re-checked on `onDidChangeWorkspaceFolders`), so clangd is up before the first file opens; a workspace without them starts and downloads nothing. At activation the shared store (`getToolchainStore`, `prefetch()`) downloads the whole toolchain except the `pch-*` variants in the order IntelliSense, compile, link, debug (`PREFETCH_ORDER`: clangd, its sysroot and flags, clang, llvm-ar, lld, lldb reactor). The IntelliSense files go through a normal `ensure` (notification with Cancel); the rest follow one file per queue turn, so a foreground request waits for at most one (status-bar progress, failures only logged, skipped offline and under Data Saver). Each file fires `onDidHaveFile` when it is cached, downloaded or not, and `clangd.wasm`, `clang.wasm` and `lld.wasm` are compiled into the shared in-memory module cache (`getModule`) then, in parallel with the next download, so a first Build or clangd start does not pay the multi-second `WebAssembly.compile`. `clangd.wasm` is compiled at once; `clang.wasm` and `lld.wasm` wait until clangd has shown its first diagnostics (`markIntelliSenseSettled`; also on a clangd failure, IntelliSense off, or after 20 s), because compiling them beside clangd's start-up delays it by ~0.5 s and a Build right after opening a file is rare. The lldb reactor is fetched but built from bytes by the debug adapter.
The loader (`toolchainDownload.ts`, `toolchainStore.ts`): the extension pins one SHA-256, of the toolchain's `manifest.json` (`toolchainPin.ts`, written by `scripts/make-toolchain-dist.mjs --pin`). The manifest lists each file's final size and hash plus its payload chunks (each with its own size and hash; `clang.wasm`/`lld.wasm` payloads are zips, `sysroot.zip` and `compile-flags.json` are raw). Chunks download four at a time with retries (not on 4xx other than 408/429), each verified before use; the result is unzipped, checked against the file hash, and only then written to `globalStorageUri/toolchain/<manifest hash>/`. A cached file is trusted only if its size and hash match, so an interrupted download resumes per file and a pinned toolchain works offline. Other cached versions are deleted after a successful download. One notification shows progress for everything still missing (cancellable; completed files are kept). The sysroot stays cached as its zip; unzipping into the memory file system happens once per session. The application-scoped setting `vscwclang.toolchainUrl` replaces the host and skips the pin (development; a workspace cannot set application-scoped settings), and is how tests and local runs use `llvm-artifacts/mtdist`. If the pinned hash is ever empty, `build()` fails with a message that says so.

Hosting layout: the unchunked, generic artifacts (`clang.wasm`, `lld.wasm`, `lldb.wasm`, reactor, sysroot) are GitHub releases of the `Ambeco/llvm-project` fork, the source of truth. What the extension downloads is served from a separate public repo (`Ambeco/llvm-artifacts`, files under `mtdist/`): the chunked/zipped copies produced by `scripts/split-wasm.mjs` / `scripts/zip-wasm.mjs`, `compile-flags.json`, and a manifest with SHA-256 hashes, fetched through jsDelivr or raw.githubusercontent.com at an immutable tag per toolchain version (e.g. `https://cdn.jsdelivr.net/gh/Ambeco/llvm-artifacts@v24.0.0/dist/...`). The extension pins the tag, so a toolchain change ships as an extension update. The toolchain repo is kept small by publishing each version as an orphan commit (or force-pushing a branch), never accumulating history; chunks stay at 16 MiB, well under per-file caps. Only extension-specific files (`compile-flags.json`, manifest) belong to this layout; this extension repo holds no binaries.

## Three environments (read before changing hosting or any filesystem)
Any change to host code (`src/web/host/`, `runProgram.ts`, `toolchain.ts` `runTool*`, mounts, environment variables, working directories) must be analyzed against each of these environments separately, and the change's description (commit message or design note) should say how it affects each. A change can be right for one and invisible in another: the constant inode in `filestat` broke only clang's include search, never a user program.

1. **Extension host (our TypeScript).** A web extension host Worker: no Node `fs`, no real OS paths. It reaches files only through `vscode.workspace.fs` (the user's folder and any provider's scheme), `ExtensionContext.globalStorageUri` (the toolchain cache, and the backing for `/tmp` and `/home/user`; durability on vscode.dev is unverified), and plain in-memory objects (the unzipped sysroot, `/obj`). OPFS, raw IndexedDB, `localStorage` and the File System Access API are not used directly (VS Code's providers sit on top of them). This is the only side that can touch real files; everything the other two see is served from here, one RPC at a time.
2. **Tool guests** (`clang`, `wasm-ld`, later `clangd`, `llvm-ar`, the lldb reactor). Our binaries, run on the host by `runTool` / `runToolOnWorkerHost`. Mounts: `/workspace` (read-write), `/sysroot` and `/resource` (read-only, in memory), `/obj` (read-only, in memory), `/out` (only when the output is outside the workspace). Empty environment, no cwd (all paths are absolute), no `/tmp`, `/home`, `/etc` or `/dev`; stdio is not a terminal (clang writes objects to stdout, clangd speaks LSP over it). clangd additionally needs a writable `/tmp`.
3. **User-program guests** (the program the user built, run by `runProgram`). Mounts: `/workspace`, writable `/tmp` (emptied per run) and `/home/user` (kept), no `/etc` or `/dev`; `HOME`, `TMPDIR`, `USER`, `LANG` plus `vscwclang.run.env`; cwd `/workspace` through the linked helper's `chdir`; stdio is a terminal (`isatty` true, so stdout is line-buffered), also under Debug and with `internalConsole`. Debug runs this same environment (`workerProgramEnvironment`) under the debug stub.

### Wasmer run host (optional; Run only)
`vscwclang.run.host: wasmer` runs the built program in a Wasmer (WASIX) sandbox instead of the Worker host; Debug, the tool guests and clangd always use the Worker host, so the core never depends on it. `runProgram.ts` branches to `runOnWasmer`; `wasmerProcess.ts` (vscode-free, node-tested) wraps a sandbox as a piped process; `wasmerLoader.ts` loads the SDK and adapts the workspace folder; `workspaceSync.ts` (vscode-free) does the copying. The SDK cannot be bundled (it fetches its own wasm and starts module Workers relative to its URL), so it is `import()`ed at run time from `vscwclang.wasmerSdkUrl` (`dist/index.js`) behind a lazily installed shim that turns module Workers into classic ones that `import()` the URL, because VS Code wraps extension-host Worker URLs in `importScripts`. An empty or unreachable URL is an error with a did-you-mean; there is no silent fallback to the Worker host.

How it differs from the Worker host, per environment:
1. **Extension host.** It owns the sandbox and the copy. The sandbox filesystem is in memory, accepts only paths under `/workspace`, and is not `vscode.workspace.fs`, so the workspace is copied in before each run (skipping `.git`, `node_modules`, `.vscwclang`; refused over 256 MB with a message) and only changed or new files are copied back after it, also after a trap. A file the program deleted is deleted on the host only if the host copy is unchanged since the copy-in; a file edited in the editor during the run is never overwritten and is reported. Files therefore appear when the program ends, not while it runs.
2. **Tool guests.** Unaffected.
3. **User-program guests.** cwd `/workspace`, `HOME`, `TMPDIR`, `USER`, `LANG` as before; `/tmp` is the sandbox's own and vanishes with the run; no persistent `/home/user`; stdio is a terminal (`isatty` true, also when piped). Preview 1 and wasi-threads modules run unmodified. A trap rejects the run with a `RuntimeError`, mapped to the same `trapped` outcome and exit code 139; `abort()` still exits 134 through the linked helper. Programs gain nothing yet: `system()`, `popen` and `fork` still fail to link because the sysroot has no WASIX libc shim.

Facts that bound every decision:
- The browser's WebAssembly engine provides no filesystem, clock, random source, terminal or environment: a module only has the imports we give it. The WASI preview 1 implementation (`GuestWasi`) is entirely ours, so every path, device and errno a program sees is something we chose to fake or to refuse.
- Faking a little is predictable (a program fails at once and the user adjusts); faking a lot makes each unfaked corner a subtle, hard-to-debug difference. Prefer failing loudly (an errno plus a message naming the path and a did-you-mean) over a plausible-but-wrong imitation, especially for anything a debugging user will rely on.
- A missing path is a deliberate answer: a program probing `~/.config/...` or `/etc/...` gets `ENOENT` (it works, there is simply no file); a path outside every mount is refused with `EACCES` and a message that lists the mounts.
- Tool guests and user programs share the host code (`GuestWasi`, `MountedGuestFs`, `VscodeGuestFs`) but not their mount tables, environment or cwd. Anything added for one must be checked against the other: a mount added to the program's table is visible to the program, and a mount added to the tools' table is visible to the compiler (a stray file under `/workspace` can change a build).
- Anything outside the workspace that guests share must be content-addressed or per-run, because several tabs and devices can run at once (see "Build artifacts").

Current incompatibilities with a general POSIX userland (such as CPython built for WASI as a Make/CMake helper, a far-future aspiration): there is no `/etc`, `/usr`, `/proc` or `/dev` (not even `/dev/null` or `/dev/urandom`; random comes from `random_get`); no processes, `fork`, `exec`, pipes between programs or signals (`system()` and `popen` fail at link time); no shell; no symlinks or hard links; no file permissions or ownership beyond success or `EACCES`; no sockets; the working directory is a libc-level `chdir` shim, not a host feature; WASI preview 1 only (no emscripten JS glue). A CPython port would need its own mount layout (stdlib under a read-only mount, a `/usr`-style prefix) and the spawn and pipes work listed under "Processes" in `remaining_work.md`. We have committed neither to implementing nor to abandoning the CPython/Make aspiration. Environment and filesystem decisions should move toward compatibility where that is cheap, and must not close the door needlessly. The aspiration is dropped only when a concrete decision turns out to be impossible to reconcile with it; that decision is the moment to record the abandonment here, with its reason.

Open layout decisions (one shared emulated filesystem for tools and programs, where the project, build outputs and `~` live, which `/dev` and `/etc` entries to fake) are tracked in `remaining_work.md` "Guest filesystem layout"; until decided, the mount tables above are the contract.

### Guest filesystem: concerns and candidate layout (undecided)
Concerns that any layout must answer, from the project owner:
- User programs plausibly expect a *nix-like filesystem for at least global and user configuration lookups (`~/.config`, `/etc`), and many test and build scripts expect `/tmp`, `/dev/null` and `/dev/urandom`. The engine supplies none of it; we fake what we choose to.
- How much *nix to fake so a reasonable share of C++ programs can be run and debugged. Too little: some programs are not debuggable, but users are not surprised. Too much: each unfaked corner becomes a subtle, hard-to-diagnose difference while debugging. Failing loudly is preferred over being subtly wrong, so fake a small, well-defined set and refuse the rest explicitly.
- Simplicity: tools and user programs sharing one emulated filesystem (different working directories, possibly different permissions) would mean less code, fewer bugs and less drift than separate mount tables, at the cost of the compiler seeing what programs can write.
- Candidate layout: the project mounted at `/home/shared/src/<project>` as the tools' working directory; intermediate objects, archives and shared objects defaulting to `/tmp` (or whatever Make/CMake use by default); final binaries to `./build/` (or the Make/CMake default); the user program running with `/home/vscw` as `~` and working directory, able to read (and perhaps write) the source tree at its shared path.
- Cheap, likely-needed entries: `/tmp`, `/dev/null`, `/dev/urandom` (or an equivalent `random_get` mapping).
- Far-future Make support (possibly a separate extension) may want CPython (`wasm32-emscripten`/WASI) for build and test scripts, which expects specific paths and a process model. It is currently incompatible (see the list above); the aspiration is neither committed to nor abandoned, and is dropped only when a decision proves infeasible to reconcile with it.
Each decision here is checked against the three environments separately, and decisions move from this list into the mount tables above once made (open items: `remaining_work.md` "Guest filesystem layout").

## Host
Build runs a single-process `clang.wasm` (cc1 in-process; the `mtdist` layout's is the wasi-threads build, run with `-fintegrated-cc1`) up to `vscwclang.parallelCompiles` sources at a time, each in its own Worker (the debugger's lldb reactor, which runs in-process on the extension host, gets its pool threads from `WorkerThreads`), and `lld.wasm` on the Worker host (below), orchestrated by the extension. `toolchain.build()` compiles each source with `clang++`/`clang` (`-c -o -`: clang writes each object to stdout, the host puts it in an in-memory file system mounted read-only at `/obj` for `wasm-ld`, so only the final `.wasm` is written to the workspace), keeps going after a failed compile so all diagnostics are reported, then links with `wasm-ld`. User flags are checked first by `flagPolicy.ts` (rejections carry did-you-mean text); clang/wasm-ld text output is parsed by `diagnostics.ts` and published by `diagnosticsCollection.ts`: the Problems panel is cleared when a build starts and refreshed after each source compiles (`BuildRequest.onDiagnostics`), so errors appear before later files finish; the final publish from the finished result is authoritative. Compiled `clang.wasm`/`lld.wasm` modules and the unzipped sysroot are cached in memory across builds. Each tool is a fresh Worker with `vscwclang.toolTimeoutSeconds` as its timeout. Spawned cc1/wasm-ld are not done (they need the host's spawn hook); the threaded `clang.wasm` runs `-fintegrated-cc1`.

**Slices.** `build()` compiles and links user programs for `wasm32-wasip1-threads` by default (`chooseSlice`, `threadSlice.ts`: shared memory, `-pthread`, the threads sysroot, its PCHs and shims), because libc++ without it has no `<thread>` or `<mutex>` and libraries that only include them would not compile. `vscwclang.threads: false` selects the plain `wasm32-wasip1` slice; `-pthread`/`-lpthread` in any flag list selects threads regardless. clangd's fallback flags use the same choice. Compiled shims are cached per slice.


### Worker host (`src/web/host/`; Build, Run, clangd and Debug all run on it)
- `wasiGuest.ts` (`GuestWasi`, vscode-free): WASI preview 1 over a synchronous `GuestServices` interface. Regular files are read whole on open and written back when the last descriptor closes, on `fd_sync`, and at exit or trap; a trap or `proc_exit` never escapes, `start` returns the outcome. `..` cannot leave a preopen. With `terminal` set, stdio reports a character device without `FD_SEEK`/`FD_TELL` rights, which is what wasi-libc's `isatty` checks; without a tty, libc fully buffers stdout after its first flush, so output printed before a breakpoint or a long computation would not show.
- `syncChannel.ts`: a Worker posts a request and blocks in `Atomics.wait`; the extension host (`SyncRpcServer`) answers into a 256 KiB shared buffer in as many chunks as needed. Output is fire-and-forget. One channel per Worker.
- `guestWorker.ts` / `guestWorker.web.ts`: the Worker entry (`RpcGuestServices` forwards to the channel); bundled to `dist/web/host/guestWorker.web.js` and started from a blob URL (`workerHost.ts`).
- `guestProcess.ts` (`GuestProcess`, vscode-free): owns the Worker, serves its requests from a `GuestFileSystem` and a `StdinQueue`, and resolves `run()` with exit, trap, failed or terminated. `vscodeGuestFs.ts` is the `GuestFileSystem` over `vscode.workspace.fs` and a mount table (`/workspace`, `/tmp`, `/home/user`); `programTerminal.ts` is the line-mode terminal shared with Debug. `workerProcess.ts` (`createWorkerProcess`) wraps a `GuestProcess` in the `PipedProcess` shape (`stdin.write`, `stdout/stderr.onData`, `run`, `terminate`) that clangd and Debug use, so each has one code path for both hosts; a trap ends `run()` with 139 and a stderr line, `terminate()` with 130.
- wasi-threads (`GuestProcessOptions.sharedMemory`, from `createSharedMemory(wasmBytes)`, which reads the imported memory's limits out of the binary): the Worker gets the shared memory as `env.memory` and a `wasi.thread-spawn` that takes a thread id from a shared counter, posts a `spawnThread` request and returns at once. The extension host (`GuestProcess.spawnThread`, via `createThreadWorker`) creates the thread's Worker, which instantiates the same module on the same memory and runs `wasi_thread_start`; each thread has its own `SyncRpcClient` channel, served by the same handler. A thread reports back only if it ends the process (`proc_exit`, a trap), and `finish` terminates every thread Worker. Each thread has its own `GuestWasi`, so its own descriptor table: file I/O must stay on one thread (the fork's `wasi_threaded_io` shim does that for `-pthread` programs); stdout/stderr work from any thread. Fixture: `fixtures/host/threads.c`.
- `mountedGuestFs.ts` (`MountedGuestFs`, vscode-free) is the mount table; `memoryGuestFs.ts` (`MemoryGuestFs`) serves the read-only `/sysroot` and `/resource` and Build's `/obj` from memory; `UriGuestFs` serves a `vscode.workspace.fs` folder. Build mounts `/workspace`, `/sysroot`, `/resource`, `/obj` and, for output outside the workspace, `/out`.
- `GuestWasi` gives every path its own inode: clang drops include directories that share (device, inode).
- A trap ends Run with `[prog trapped: <engine message>]` and exit code 139.

### Worker rules (probed in `workerMechanics.test.ts`)
- A Worker that creates a child Worker and then blocks in `Atomics.wait` never sees the child start (Chromium). Every Worker the host needs (spawned `cc1`/`wasm-ld`, `thread-spawn` threads) is therefore created by the extension host on a message from the blocked Worker, which then waits on a SharedArrayBuffer; a pre-spawned pool would work too.
- The same channel carries all synchronous host services: a Worker posts a request, blocks on `Atomics.wait`, and the extension host (the only place with `vscode.workspace.fs`) replies into the SharedArrayBuffer and notifies. Verified, ~50 ms round trip including a deliberate delay.
## Flags, run and tasks
`request.flags` is one list; `splitFlags` (flagPolicy.ts) routes `-l`, `-L` (relative dirs resolved under `/workspace`) and `-Wl,a,b` (split into separate args) to wasm-ld, everything else to `clang -c`. `vscwclang.run` (`runProgram.ts`) builds, then runs the .wasm on the Worker host with a `ProgramTerminal` as stdin/stdout/stderr: stdin is the terminal's line mode (echo, line editing, one line per Enter, Ctrl+D for EOF); Ctrl+C or closing the terminal terminates the process. `tasks.ts` provides `vscwclang` build tasks as `CustomExecution` that print clang's text; the `$vscwclang` matcher turns `/workspace/<file>:l:c: error|warning:` lines into Problems (notes and linker lines are not matched).

## Scope
North star: compile, run and debug self-contained C/C++ programs (and a library's tests) in a browser tab with nothing installed, on machines where installing a compiler is impossible or unwanted (Chromebooks, locked-down school or work machines, tablets, `github.dev`/`vscode.dev` on a repo with no cloud VM). Non-goals: a POSIX userland (shell, coreutils), networking, GUI and native-library linking, MSVC project formats, replacing desktop toolchains. Before adding a feature, check it serves the north star; most "it would be cool if programs could ..." ideas below it belong in a later, separate project.

Framed against the desktop C/C++ (cpptools) extension this project is meant to replace entirely in the browser, cpptools plays three roles, and this extension's scope maps one-to-one:
1. **Build**, reading `tasks.json`'s default build task (`g++`/`clang++`-style) — done (design.md "Project model and integration").
2. **Debug**, reading `launch.json` (`cppdbg`/`cppvsdbg`) and implementing the Debug Adapter Protocol (a `DebugAdapterDescriptorFactory`/inline adapter registered for a debug type) — `args`/`preLaunchTask` are read for Run today, but the DAP adapter itself (breakpoints, stepping) is not implemented; see Milestones 4-6.
3. **IntelliSense** (completion, hover, go-to-definition, diagnostics-as-you-type), via VS Code's ordinary language-provider APIs — a minimal `clangd` language client is wired up (`src/web/clangd/clangdClient.ts`, Milestone 3); background indexing runs on clangd's own threads, most polish is not done (documents/remaining_work.md "V3 idea: clangd").

Make, CMake and CPython support ships in this extension's codebase (this flavor of the plugin) as optional features layered around a self-sufficient core. The core (clang, lld, the lldb reactor, clangd) must never depend on them: they are wrappers over the core's public build/run entry points, loaded only when used (optional downloadable packs, see `documents/build_systems_feasibility.md`), and removing them leaves the core unchanged. They still feed the core and clangd through the neutral `compile_commands.json` format (see "Project model and integration" below) wherever that suffices.

## cpptools settings compatibility
Where a setting has a cpptools (`C_Cpp.*`) equivalent we mirror its name and shape, and read the cpptools value as a fallback, so a project configured on desktop works here unchanged. VS Code returns settings.json values for unregistered keys, and cpptools has no web build, so `C_Cpp.*` is read straight from `getConfiguration('C_Cpp')` (`projectConfig.ts`: `userFlags`, `loggingLevel`, `intelliSenseEnabled`; `isUserSet` uses `inspect()` to tell a user value from our default). Mapping is vscode-free in `toolchain/cppToolsSettings.ts`:
- Variables in settings: `vscwclang.flags`, `run.args`, `run.env` values and the `C_Cpp.default.*` flag entries go through `projectModel.resolveVariables` (`projectConfig.ts` `resolveSettingStrings`), the same expansion `tasks.json`/`launch.json` get: `${workspaceFolder}` (and `${workspaceRoot}`, `${cwd}`) is `/workspace`, because the compiler and program see guest paths. An unsupported one (`${env:}`, `${command:}`, `${file}` with no editor) throws naming the setting and entry, except for clangd's startup flags (`userFlags(log, true)`, no active file) and `C_Cpp` entries, which are dropped with a note. Host-relative globs and paths (`sourceGlobs`, `compileCommands(.include)`, `files.exclude` keys) just drop a leading `${workspaceFolder}/` (`stripWorkspaceFolder`).
- `vscwclang.flags`, when the user has not set it, becomes its default plus flags from `C_Cpp.default.defines`, `includePath` (workspace paths only; `${workspaceFolder}` becomes `/workspace`, `/**` is read as the directory), `cppStandard` (`c++NN`/`gnu++NN`), `cStandard` (`cNN`/`gnuNN`) and `compilerArgs`. The two standards apply only to sources of their own language (`BuildRequest.languageFlags`, placed before `flags` so a user `-std=` wins); clangd gets them from its user config instead (next bullet). `C_Cpp.default.forcedInclude` becomes `-include <file>` (workspace files only; an `-include` also switches the PCH off). `.vscode/c_cpp_properties.json` (JSONC, `toolchain/cppProperties.ts`, read by `readCppProperties`) is laid over those settings key by key, as in cpptools: its first configuration (there is no picker) wins for `defines`, `includePath`, `forcedInclude`, `compilerArgs`, `cppStandard` and `cStandard`, and its `compileCommands` sits between `vscwclang.compileCommands` and `C_Cpp.default.compileCommands`; `compilerPath`, `intelliSenseMode` and similar are ignored, and a `configurationProvider` is noted. Setting `vscwclang.flags` explicitly replaces this entirely, as does `vscwclang.useCppToolsSettings: false`. Unmappable entries are dropped with a did-you-mean line in the output channel. Build and the clangd `fallbackFlags` share `userFlags`.
- `vscwclang.files.exclude` (replaces the old directory-name list `sourceExclude`) is a glob object like `C_Cpp.files.exclude`, which is merged in (the setting the user actually set wins a conflict; `false` un-excludes). `toolchain/sourceFilter.ts` `makeSourceExcluder` supports `**`, `*`, `?`, `{a,b}`, ignores case, anchors globs without `**` at the workspace folder, and excludes a path when its own glob or any ancestor folder matches; `when` objects are ignored. Build and the index sweep share it (`projectConfig.ts` `sourceExcluder`); files named explicitly by a task or database are never excluded.
- `vscwclang.compileCommands` is string or array like `C_Cpp.default.compileCommands` (first non-empty entry used, `${workspaceFolder}/` stripped), falling back to that setting.
- clangd settings (`clangd/clangdSettings.ts`, vscode-free; `clangdClient.ts` applies them at startup, so changes need a reload): a generated `config.yaml` in extension storage, mounted at `/config` with `XDG_CONFIG_HOME`, holds what `fallbackFlags` cannot express. With no compilation database (a database entry stays authoritative, and a `-std` in `vscwclang.flags` wins): `.h` gets `-xc++-header` unless the workspace has C sources and no C++ ones (`headersAreCpp`; clangd otherwise reads `.h` as Objective-C++), and `C_Cpp.default.cppStandard`/`cStandard` apply `PathMatch`ed to their own languages' files. `C_Cpp.refactoring.includeHeader: never` becomes `-header-insertion=never`; `codeAnalysis.clangTidy.enabled: false` becomes `-clang-tidy=false`, and `checks.enabled`/`checks.disabled` become the config's `Diagnostics: ClangTidy: Add/Remove`. These C_Cpp keys are contributed with a `null` default so an unset value changes nothing. The other `clangTidy.*` keys only log a note. `C_Cpp.inlayHints.parameterNames.enabled` and `autoDeclarationTypes.enabled` become the config's `InlayHints: ParameterNames/DeducedTypes` (contributed with a `null` default, since cpptools defaults them off and clangd on); the other `inlayHints.*` keys only log a note. clangd reports some tidy findings (`modernize-use-nullptr`) as Hints, which VS Code never lists in Problems, so `handleDiagnostics` raises `source: clang-tidy` Hints to Warnings (`tidySeverity.ts`), matching cpptools and the clangd extension. YAML strings are single-quoted because clangd's reader rejects a backslash escape in double quotes. Formatting needs no extra binary: clangd links clang-format, and `LanguageClient` registers the document, range and on-type formatters from its capabilities. `C_Cpp.clang_format_fallbackStyle` becomes `-fallback-style=` (`Visual Studio` -> `Microsoft`, the nearest predefined style, since clang-format has no preset of that name); `C_Cpp.formatting: disabled` is enforced in client middleware that returns no edits, because the formatter stays registered. The same middleware skips read-only `vscwclang-toolchain:` documents. clangd has no `-style=`, sort-includes or binary-path option, so `clang_format_style` other than `file`, `clang_format_sortIncludes`, `clang_format_path` and `formatting: vcFormat` are only reported in the log.
- `vscwclang.loggingLevel` (None/Error/Warning/Information/Debug, default `C_Cpp.loggingLevel`) picks clangd's `-log=` level (error/info/verbose) and whether clangd's stderr is echoed to the output channel.
- `vscwclang.intelliSense.enabled` (default off when `C_Cpp.intelliSenseEngine` is `disabled`) skips starting clangd. Both it and `loggingLevel` need a window reload.

## Run environment
User programs run on the Worker host (WASI preview 1). A program sees only what is mounted: the workspace at `/workspace`; writable `/tmp` (emptied before each run) and `/home/user` (kept), both `vscodeFileSystem` mounts of directories in extension storage; there is no `/etc` or `/dev`. The environment is `HOME=/home/user`, `TMPDIR=/tmp`, `USER=user`, `LANG=C.UTF-8` plus `vscwclang.run.env` (`null` removes a default). WASI has no cwd, so a constructor in the helper object linked into every program (`ABORT_SHIM_SOURCE`) calls `chdir("/workspace")`, making relative paths resolve there. C++ builds also link a `--wrap=__main_void` shim (`UNCAUGHT_SHIM`) that calls `std::terminate` from a `catch (...)` around `main`, because with `-fwasm-exceptions` an uncaught `throw` otherwise escapes `_start`; libc++abi's handler then prints the type and `what()` and `abort()` exits 134. A throw outside `main` (a static constructor) still escapes and the host reports it as a crash (139) without a type. Arguments come from `vscwclang.run.args`, or from the prompt of `vscwclang.runWithArgs` (shell-style quoting, `splitArgs`; last answer kept in workspace state). Sockets are stubbed (`sock_*` return not-implemented; preview 1 has no `connect`), and there are no processes or signals. Mount kinds available: workspace folder, any VS Code file system (writable), extension files, and an in-memory file system (read-only to the guest). Terminal input is line mode (`ProgramTerminal`): Enter delivers a line, Ctrl+D ends stdin, Ctrl+C stops the program.

Default flags (`DEFAULT_COMPILE_FLAGS`, `DEFAULT_C_COMPILE_FLAGS`, `DEFAULT_LINK_FLAGS` in `defaultFlags.ts`, placed before user flags): `_WASI_EMULATED_{SIGNAL,GETPID,PROCESS_CLOCKS}` with their libs, C-only `-mllvm -wasm-enable-sjlj` with `-lsetjmp` (so `setjmp`/`longjmp` work), and an 8 MiB stack (the wasm-ld default overflows in template-heavy code and traps as `memory access out of bounds`). `_WASI_EMULATED_MMAN` is deliberately not defaulted, since its mmap silently drops writes.

Library-level behavior (wasi-libc, verified by building and running under Node WASI): `fork` and `popen` are undeclared, so using them is a compile error; `system()` is declared but undefined, so it is a link error (`undefined symbol: system`); `msync` is a link error; `mmap` needs `-D_WASI_EMULATED_MMAN` and `-lwasi-emulated-mman` and only emulates reading (file contents are copied into memory): a write through a `MAP_SHARED` mapping is silently NOT written back to the file. `fopen("/tmp/...")` works through the `/tmp` mount. A failed `assert`, `abort()` or `std::terminate` exits 134 through a weak `abort()` helper linked into every program, since a trap would hang `run()`.

## Build artifacts
Compiled objects are kept in `objectCache.ts` (`ObjectCache`) over a `ByteStore`: the browser's Cache API (`vscwclang-objects-v1`, on disk in the browser profile) when `caches` exists, else memory for the session. `build()` compiles with `-H`, strips the include trace from the diagnostics, and stores each successful object (keyed by its content hash) with the warnings it produced and a content hash of every `/workspace` header it included; a small index (arguments, source and header hashes, size, last use) is written every 5 seconds while objects are stored and by `flush()` at the end of each build (also on a thrown error), so a build that dies midway keeps the objects it finished. A source is reused while its compile arguments, toolchain manifest hash, own content hash and header hashes are unchanged; failed compiles are never cached, but the successful ones of a failing build are kept. A link whose object ids, arguments and output are unchanged, and whose output file still has the recorded mtime (kept for the session only), is skipped too, so an unchanged tree builds without starting a tool, and an edit that changes no object byte (a comment) does not relink. Entries unused for `vscwclang.buildCache.maxAgeDays` (default 7), then the least recently used past `vscwclang.buildCache.maxSizeMB` (default 1024), are dropped and their objects deleted; `vscwClang: Clear build cache` removes everything. The browser may still evict the whole origin under storage pressure, which costs only a recompile (and the toolchain download). Two tabs share the cache but each writes its own index, so one can delete the other's newest objects as unreferenced: a recompile, never a wrong object. Headers that did not exist at compile time (a new header earlier on the `-I` path) and files read with `__has_include` are not tracked. Storage write failures (quota) leave a source uncached. The linked `.wasm` and `build.log` go where the user can reach them (`chooseArtifactDir` in `buildWorkspace.ts`; the policy is in `artifactPolicy.ts`: `isWritableFileSystem(scheme)` is not false and the scheme is not a virtual-repo one; an unknown writability is tried and falls back on failure). When the output is outside the workspace it is a `vscodeFileSystem` mount at `/out` for wasm-ld; an explicit task `output` stays workspace-relative. For local, writable folders: inside the folder (under `.vscwclang/<mode>/`, so debug and release builds from two tabs or two synced devices do not collide); this also lets a synced folder share them across devices. For read-only or virtual folders (`vscode-vfs://` repos, where a written file would also show up as a pending change in Source Control) they go in extension storage instead, which lets read-only repositories build and run. A task's `output` overrides the location; a dedicated setting is not provided. Caches shared between devices must be content-addressed (hash of source, flags and toolchain) so concurrent writers cannot clash.

## Precompiled headers
Every recompiled C++ file pays the full libc++ parse (`<iostream>` alone is ~1 s), so the toolchain ships PCHs of 30 common headers (`pch.ts` `PCH_HEADERS`; no `<cmath>`, `<cassert>` or C headers, whose names would collide with user globals or whose behavior depends on `NDEBUG`). `scripts/make-toolchain-dist.mjs` builds one per `-std` (gnu++17 = clang's default, c++17, gnu++20, c++20) and per `-O` level (0, 2) with the layout's own shipped `clang.wasm`, lists them in `compile-flags.json` under `pch.<slice>` and in the manifest as `pch-<std>[-O2].pch` (zip payloads, ~9-11 MB each). They are not in `BUILD_FILES`: a build downloads only the variant it uses, and builds without it if that fails or the toolchain lists none (older pins, `--no-pch`).

A PCH records its source header and every input file's size and mtime, so the dist script puts the header in `sysroot.zip` (`/sysroot/vscwclang/pch.h`) and builds against a copy of the sysroot with all mtimes 0, which is what `MemoryGuestFs` reports; `-fvalidate-ast-input-files-content` makes clang fall back to content hashes if they ever differ. The script then compiles a source against each PCH, with no `-std` for the default one, so a PCH clang rejects fails the publish.

`selectPch` (`pch.ts`, vscode-free) decides per source, from the user-supplied flags and the source text. Clang rejects a mismatched `-std`, `-O`, `-fno-exceptions`, `-fno-rtti` and similar with an error, but silently accepts what the PCH's headers already consumed, so those skip the PCH: `-D` of a reserved name (`_*`) or `NDEBUG`, any `-U`, `-include`, `-imacros`, `-undef`, `-x`, `-ffreestanding`, `-Xclang`, and a `#define`/`#undef` before the first `#include`. It is also skipped for C, for the helper shims, and for a source that includes nothing the PCH holds (loading the 15 MB PCH costs ~0.4 s, more than a `<cstdio>`-only file saves). The PCH goes to the compiler as `/obj/<file>` with `-include-pch`.

Two semantic differences remain, both documented in the setting's description: the PCH's headers count as included at the top of every such file, so a missing `#include` compiles here and fails elsewhere; and the PCH's C headers declare names (`rand`, `time`, `remove`, `exit`, `div`, ...) a bare `#include <vector>` does not, so a user global of that name fails. `pchRetryable` recognizes those clashes (and clang rejecting the PCH) in the compile's errors and the file is compiled again without the PCH; the second result is the one reported and cached, under the arguments that selected the PCH, so the next build does not repeat the failed attempt. Ordinary errors are not retried. `vscwclang.precompiledHeaders` turns the feature off.

## Project model and integration
Goal: a desktop VS Code project that builds with clang should build, run and debug the same here. `toolchain.build(request)` (sources, flags, output, mode) stays the only boundary to the compiler; a "project model" step in front of it turns what the workspace already contains into that request. This extension owns the clang-compatible inputs desktop VS Code uses: `tasks.json` (tasks that call `g++`/`clang++`, mapped through `flagPolicy`) and `launch.json` (`program`, `args`). Solution and project files (`.sln`, `.vcxproj`) are out of scope because they almost always target non-clang compilers and flags.

`toolchain/projectModel.ts` (vscode-free, node-tested) does the mapping; `projectConfig.ts` reads the configuration through `workspace.getConfiguration('tasks' | 'launch', folder)` (never by parsing the files, which are JSONC). Variables resolve straight to guest paths (`${fileDirname}` is `/workspace/src`), so mapped flags are already valid for the compiler; unsupported variables, other compilers and unmappable arguments throw with a did-you-mean. `${file}` means the last C/C++ editor (`trackActiveCppFile`), since a focused terminal has no active editor. A task's flags replace `vscwclang.flags` and its sources replace `sourceGlobs`; the task's `-o` only names the `.wasm` (stem plus `.wasm`), which goes where the artifact policy says, so read-only folders still work and Run always runs what it built (`launch.program` is only used to find the task whose `-o` matches). `-g` selects debug mode. Dropped with a logged note: colour flags (they would put ANSI codes in the text the problem matcher parses), `-pthread`, `-static`, `-lstdc++`, `-m64`, `-mwindows`.

Which task and arguments apply: Build uses the default build task if it runs a g++/clang++-style compiler (a default task running `make` or `cl.exe` is skipped with a log line; a compiler task that cannot be mapped is an error), else the `vscwclang` settings. Run picks a `launch.json` configuration of a C/C++ debugger type (QuickPick when several, last choice first), then the build task from its `preLaunchTask`, else the task whose `-o` matches `program`, else the default build task, else the settings. Launch `args` (when the key exists) win over `vscwclang.run.args`; the explicit "with Arguments" prompt is pre-filled from them. Tasks of type `cppbuild` are also resolved by the task provider (so the Tasks menu runs them); `shell` tasks cannot be intercepted by a provider and are mapped only by the Build and Run commands. Launch `cwd` and `environment` are not applied.

Make, CMake and CPython are optional wrappers inside this extension (see "Scope"); other build systems (Bazel, Meson) would belong in separate extensions, since nothing can run as a native process on the web. Both integrate through `compile_commands.json`, the neutral compilation-database format (`directory`, `command` or `arguments`, `file` per translation unit) already read by clangd and cpptools: this extension reads it as one more source of build plans, so any tool that emits it works with no code dependency. A versioned exported API (like the Git extension's `getAPI(1)`) and a command accepting a plain-data build request are the tighter options if needed later; the `vscwclang` task type is already a declarative form of the same request.

`compile_commands.json` is the third build source: Build and Run use the default `tasks.json` build task if it maps, else the database (`vscwclang.compileCommands`, else `compile_commands.json` or `build/compile_commands.json`), else `compile_flags.txt` (flags for every source, which still come from `sourceGlobs`), else the settings. The C/C++ extension only uses the database for IntelliSense, so build behavior follows CMake Tools instead: each source is compiled with the flags of its own entry (`BuildRequest.sourceFlags`; `-l`/`-L`/`-Wl,` flags found there are merged into the one link), and a database that names several CMake targets (object paths under `CMakeFiles/<target>.dir/`) shows a picker like CMake Tools' build target, last choice first, with "all targets" as an item. A database without targets (Bear, Make) links every entry; `vscwclang.compileCommandsInclude` globs narrow that. Entries are mapped by `planFromCompileCommands` with the same argument handling as tasks, minus the database's own mechanics (`-c`, `-o`, `-MD`/`-MF`/`-MT`, `ccache`/`sccache`/`distcc` wrappers); a second entry for a file, non-C/C++ files and entries outside the workspace are skipped with a logged note, and response files (`@x.rsp`) are errors. Databases are usually generated elsewhere, so absolute paths are rebased: they map under the workspace folder if they lie in it, else `inferHostRoot` finds where the folder sat by matching the longest tail of a source path that exists here (Windows paths and drive-letter case are normalized). Include directories outside that root (`/usr/include`, vcpkg) are dropped with a note instead of failing, since the sysroot provides the standard library and the compile error then names the missing header. Other unmappable flags (`-march=native`, `--target`) are errors, as for tasks. The database is usually gitignored, so it is mostly useful for local folders, not `github.dev`.

## Debug stub channel
Debug builds link `src/web/debug/debugStub.c`, the program-side half of debugging, kept in the program so the host needs no custom import. It is the `__sanitizer_cov_trace_pc_guard` hook (exported by the linker so `scanProgram` finds the call sites), so the program imports only WASI functions. It keeps a shadow call stack of (guard, `__stack_pointer`) per instrumented frame, checks breakpoints by a bit in the guard word itself (no table lookup), and supports step into/over/out by comparing stack pointers. Debug builds add `-mllvm -sanitizer-coverage-stmt` (passed when `compile-flags.json` has a `debugCoverage` entry; the llvm-project fork's `SanitizerCoverage.cpp`), which puts an extra guard, calling the same hook, before the first instruction of every source line that starts inside a basic block and right after each call that has more code on its own line, so a guard exists for nearly every line and a return lands back on the call line. Stepping stops at each hook; the adapter repeats while the line and frame are unchanged. With an older toolchain (no `debugCoverage`) guards stay per block and the notes in the next paragraph about block granularity apply.

The channel is the program's own stdio. At startup the stub sends `hello` and blocks in `fd_read` until the host releases it, so breakpoints are armed before any user code runs. Stub to host: frames `ESC _ vscw <text> ESC \` inside stderr (`stop`, `mem`, `memerr`, `error`); `FrameDemux` splits them from the program's own stderr at any chunk boundary and passes other escape sequences through. Host to stub: `vscw bp|mem|go|into|over|out` text lines on stdin, read one byte at a time so nothing meant for the program is consumed. The host writes commands only while the program is stopped and forwards typed program input only while it runs (`StubDebuggee.writeInput` queues input typed at a stop and sends it right after the resume command). Input written just before a stop can still be unread, so a stub line that does not start with `vscw ` is handed back as an `input` frame (hex bytes) instead of being an error; the host puts those bytes at the head of the queue, and a resume that followed such a write first sends `vscw sync` and waits for `synced`, which guarantees every handed-back byte has arrived before the resume command and the queue go out. Memory pages (4 KiB) are read by the stub itself (bounds-checked, so a wild address reports `memerr` instead of trapping).

What the debugger can and cannot do follows from where the hook sits. The hook runs at the start of every basic block and at every line change inside one, so a line breakpoint stops exactly on its line (with block-only guards it stops at the start of the enclosing block and the `setBreakpoints` response says so), and stepping moves line to line. A stop at a function's entry guard sees parameters before they are spilled to the stack, so a step into a call goes on to the callee's first body line (`BreakpointIndex.isEntryGuard`); a breakpoint on the `{` line still stops at the entry guard. IR has no is_stmt flag, so a statement split over several lines stops on each, and a loop whose header and body share one line is one stop. Stepping off the end of a callee stops on the call line in the caller (the post-call guard); a call with nothing left on its line returns straight to the next line's guard. Debug builds pass `-fsanitize-coverage-ignorelist` (`coverageIgnorelist.ts`, written to the in-memory `/obj` mount) that excludes C++ standard-library functions by mangled name (`_ZNSt*`, `_ZSt*`, ...; a coverage ignorelist cannot match by header path), so they have no hooks and step-in never lands in them; a user specialisation of a `std` template loses its guards too. The Variables pane lists the frame's variables and expands them through the reactor's `wasm_dbg_get_variables`, which names a value by an index path (variable number, then child numbers) rather than an expression, so data-formatter children such as a `std::vector`'s elements work too and a call can be re-run after missed memory pages are fetched. A variable that lldb cannot read (a by-value struct parameter or a VLA pointer lives in a wasm local, which no host can read) is listed with the reason as its value. A function that uses a VLA or `alloca` moves `__stack_pointer` inside its frame: `scanProgram` takes the frame-base local from clang's pinned copy of the prologue's local (`local.get A; local.set B`), and `ShadowStack` keeps the frame's entry `sp` when a non-entry guard of the same function sees a lower one. The VLA itself is still unreadable (see above). Hover, Watch and the Debug Console evaluate variable paths (`x`, `p.y`, `arr[2]`) through lldb, and anything more (`a + b`, `i == 3`) with `debugExpression.ts`, a small C-like evaluator whose variable reads go through the same lldb path formatting; breakpoint conditions, hit counts (`N`, `>= N`, `% N`, counted only when the condition held) and logpoints (`{expr}` in the message) are decided by the controller at the stop: the stub stops on the guard as usual and the controller resumes at once when the verdict is not to stop (a condition that cannot be evaluated stops and says why). Threads (all-stop, with the program's shared memory): the stub keeps the shadow stack and step state per thread (`_Thread_local`) and registers each thread in a static `registry` (id, stack addresses, state) at its first hook, so the host lists every thread and reads a parked thread's shadow stack straight out of shared memory (`stubRegistry.ts`; the `hello` frame carries the registry address). A stop sets `CTL_STOPPED` in the same `control` word as the pause bit, so the per-guard cost stays one load: every other thread parks at its next hook (`memory.atomic.wait32` on a generation word), and falls through to its own breakpoint check when the world resumes, so a breakpoint it sat on still fires. Stops are served in arrival order by a ticket lock, and a resume waits briefly for the parked threads to wake before the resuming thread runs on, otherwise a breakpoint it hits again at once would starve them. A stop also waits up to 40 ms for the others to park; a thread blocked in a lock, sleep or `cin`, or in uninstrumented code, does not reach a hook and is listed as still running with no stack (the same limit as Pause). Each `stop` frame names its thread (`1` is main). The controller announces every thread (DAP `thread` events, `exited` when one ends), reports `allThreadsStopped: true`, serves any thread's stack (frame ids of a thread other than the stopped one are `threadId * 65536 + index + 1`; Variables and evaluate switch the reactor to that thread's frames), resumes every thread on Continue whichever thread the client names, and steps only the thread that stopped (a step on another thread is an error that names the right one). Without shared memory (`vscwclang.threads` off) there is no all-stop: the stopped thread alone is known, announced when it first stops, and other threads' stacks are empty. A function breakpoint arms the function's first body guard (matched on the demangled name by `demangle.ts`), and stack frames show demangled names with `main` for the compiler's `__original_main`. The cost of a conditional breakpoint in a hot loop is one stop round trip per hit. Pause and breakpoint changes while the program runs go through the program's shared memory (every threaded program has one, created by the extension host): the host sets or clears bit 0 of a guard word with `Atomics.or`/`Atomics.and`, and Pause sets the stub's `pause_requested` word (its address is the third field of `hello`), which the hook tests on each call; the first hook to see it clears it and stops with reason `pause`, and every stop clears it so a pause that raced a breakpoint does not fire again after the resume. The host owns the bits for the whole session (no `bp` command), and writes none before the start stop because the shared-memory initialisation would zero them. A Pause only lands at the next guard, so a program blocked in `std::cin`, a sleep or a lock, or running uninstrumented `std` code, stops when it next reaches one. Without shared memory (`vscwclang.threads` off) `capabilities` say so: changes are queued to the next stop and Pause fails with an explanation. Pause while stopped is a no-op. By default (launch attribute `console`: `integratedTerminal`) the program's stdin, stdout and stderr are a terminal owned by the adapter (`ProgramTerminal` over `LineEditor`: echo, Backspace, Enter; no end-of-file key in debug), so prompts sit beside the typed answer and input reaches `std::cin`; the debug stub's own stdin cannot be the terminal because it must stay a pipe for commands. With `console: internalConsole` the output goes to the Debug Console and stdin is not connected. In terminal mode `resolveLaunchConfiguration` (`launchConfiguration.ts`) defaults `internalConsoleOptions` to `neverOpen`, because VS Code otherwise raises the empty Debug Console over the program's terminal, and the Debug Console gets one line naming the terminal (`DebugTarget.notice`). It also turns an empty configuration (F5 with no launch.json) into the default launch; without that, VS Code starts nothing.

lldb reads memory synchronously but the channel is asynchronous, so `PagedMemory` serves the current stop from a page cache, recording misses; `evaluateWithMemory` fetches the missed pages and re-runs the lldb call. lldb formats a failed read into the value text instead of throwing and keeps that result for the stop, so each re-run must first call `ReactorHost.setStop` again with the same frames. Verified on Worker host pipes (`debugStub.test.ts`) and in a worker harness with blocking stdin plus the real reactor (`stubChannel.node.test.ts`).

## Alternatives considered
### Custom JS-hook runner for Pause and live breakpoint changes
- Pros: the host would see every guard, so it could do true all-stop, trap-as-stop and exact call-site pcs.
- Cons: a new Worker runner, a hook import and a second `DebuggeeSession`; writing guard bits and a pause word in the shared memory the host already owns gives Pause and live breakpoint edits with one extra load per hook. All-stop, traps as stops and call-site pcs still need it.

### Reader thread inside the debug stub
- Pros: would apply breakpoint changes and pause while the program runs freely.
- Cons: the stub is single-threaded; stdin is shared with the program, so a reader would consume its input (the channel works only because commands and program input never overlap); does not reduce overhead, which comes from the per-basic-block hook.

### Stop every thread when one stops (all-stop)
- Pros: stable Variables and memory while stopped; matches what a native debugger shows.
- Cons: the stub only runs inside the hook of the thread that stops, so halting the others means a check in every thread's hook (cost on each guard) and a way to wake them from a thread blocked in `Atomics.wait`; it belongs with the custom runner that also gives Pause.

### Build threads only when the program asks for them
- Pros: single-threaded programs keep the smaller, non-shared memory.
- Cons: `<thread>`/`<mutex>` are missing from the plain libc++, so code that merely includes them (fmt, Catch2) fails to compile without `-pthread`; `-pthread` is still honoured when `vscwclang.threads` is off.

### Write build artifacts only to extension storage
- Pros: never touches the user's folder; works for read-only repositories.
- Cons: the user cannot reach the binary or logs, and nothing is shared across devices; used only for read-only or virtual folders.

### Parse Visual Studio solution and project files
- Pros: opens existing Windows projects directly.
- Cons: they target MSVC (`/std:`, `/W4`, Windows APIs, 64-bit assumptions), so almost none would compile with clang for wasm32 anyway; a large parser for little gain.

### Make a dedicated build-system extension call this one through a hard dependency
- Pros: simplest for the other extension; typed calls.
- Cons: couples release cycles; every build tool must know this extension. A shared file format (`compile_commands.json`) needs no coupling and also serves clangd.

### Ship the toolchain in Marketplace tooling extensions
- Pros: Marketplace signing and versioning; files served by the workbench with no CORS concerns.
- Cons: Marketplace per-vsix and per-file size caps are undocumented (reported 20-25 MB; clang alone is 24 MB gzipped), so it could need ~7 extensions kept in version lockstep; needs a publisher account per extension set; programmatic install on vscode.dev is unverified.

### Serve the chunked toolchain from this extension repo
- Pros: one repo; no extra hosting setup.
- Cons: every toolchain version's chunks (~100+ MB each) stay in git history forever, bloating clones of the extension repo; mixing binary releases with extension source makes history and tags confusing.

### Download from GitHub release assets
- Pros: natural place to publish the fork's builds.
- Cons: `release-assets.githubusercontent.com` sends no CORS headers, so vscode.dev's COEP blocks the fetch.
### Bundle the wasm binaries in the .vsix
- Pros: works offline immediately; simple.
- Cons: ~380 MB (clang, lld, lldb, lldb reactor) exceeds practical extension size limits and slows every install/update.

### Use the browser's own debugger (CDP / DevTools DWARF extension)
- Pros: no instrumentation needed.
- Cons: unreachable from a web extension host (no `chrome.*`/CDP); settled "no" in the fork's notes.

### Run a wasm interpreter to control execution
- Pros: full step control.
- Cons: large correctness surface; much slower than V8's JIT.

### Ship a separate clang-format.wasm
- Pros: could honour `clang_format_style` strings, `sortIncludes` and `--style=` exactly like cpptools.
- Cons: another ~15 MB download and a second guest to run for a feature clangd already provides through LSP; formatting would then ignore clangd's file-system view of `.clang-format`.

### Generate a `.clang-format` above the workspace for the fallback style
- Pros: could express cpptools' real `Visual Studio` preset or inline `{...}` styles.
- Cons: an invisible file the user cannot find, which also shadows clangd's own fallback; `-fallback-style=Microsoft` is close enough.
