## Milestone 1: compile in the browser
- V2 only: own Worker-hosted `clang.wasm` driver (spawn hook for `cc1`/`wasm-ld`, `$COLUMNS`) and concurrent per-file compiles; V1 `toolchain.build()` compiles sequentially on `wasm-wasi-core`.
- Persistent build cache (V1, not necessarily Milestone 1): keep object files across page reloads and days, so a returning user only recompiles changed sources. Needs durable storage (extension `globalStorageUri`, or IndexedDB if that is not durable on vscode.dev; verify), a cache key per object (source content hash, flags, mode, toolchain version, plus the headers it included, e.g. via `-MD` dependency output), and eviction. Today objects are deleted after each build and `build()` always recompiles everything.
- Threaded slice (`wasm32-wasip1-threads`) is not selectable yet; `build()` always uses `wasm32-wasip1`.
- Cancel: terminate the Worker, then call `RunInterruptHandlers()`/`CleanupOnSignal()` from JS to remove temp files.
- `wasm-wasi-core` bug ([vscode-wasm#303](https://github.com/microsoft/vscode-wasm/issues/303)): `process.run()` never settles when instantiation fails (e.g. a module importing the unimplemented `fd_fdstat_set_rights`) or when `_start` traps (`abort()`, failed `assert`, `std::terminate`, ...), because `web/mainWorker.ts` only logs the error. Mitigations: compiler/linker runs have a timeout (`vscwclang.toolTimeoutSeconds`, default 300, 0 = off), and Run refuses modules importing `fd_fdstat_set_rights` up front (`wasiImports.ts`). A weak `abort()` helper (toolchain.ts `ABORT_SHIM_SOURCE`) is linked into every program so `assert`/`abort`/`std::terminate` exit 134 instead of trapping, and Ctrl+C now prints `[terminated]` (not exit 0). Other traps in Run (out-of-bounds, `__builtin_trap`, div by zero, stack overflow) still hang silently (indistinguishable from waiting on stdin, so no timeout); Ctrl+C ends it. Complete fix: our own Run host (V2) or an upstream try/catch around `_start()`; see notes.md 2026-10-07. Untested: the timeout path itself. `--no-gc-sections` (also as `-Wl,...,--no-gc-sections` or `-Xlinker`) is rejected in `flagPolicy.ts`; remove that once fixed upstream. Other routes (`--whole-archive`, `--export-all`) may still pull the import in; a post-link import scan is the complete guard. Other `-Wl,` flags are passed through unchecked.
- Source selection: the Build command links every matching file into one program; `vscwclang.sourceGlobs`/`files.exclude` (defaults skip IDE scratch and build dirs) are the only control. Consider a project-file or per-target selection (a `tasks.json` schema for named targets) and a prompt when several files define `main`.
- Build still lets wasm-ld write the final `.wasm` directly (workspace or `/out` mount); consider routing it through memory (check `wasm-ld -o -`) and writing it from the host. Objects live in memory only (a persistent on-disk object cache is the Persistent build cache item above; other stores to evaluate: OPFS, IndexedDB, CacheStorage; localStorage is too small).
- Linker messages name the in-memory object (`/obj/0-x.cpp.o: undefined symbol: f()`); map it back to the source file. wasm-ld `>>>` detail lines only appeared in the hand-written parser tests, not in real output (no debug info in release mode).

- C++ exceptions: the toolchain's libc++ is the `noeh` build and clang runs with `-fno-exceptions`. A survey of 90 old standalone files (2026-10-06) found `throw`/`try` blocking six of the projects that otherwise got furthest; an exception-enabled slice (wasm exception handling, needs the fork's libc++/libc++abi built with EH and a host that supports the wasm EH proposal) would unlock much real-world code. Decide if and when.

## Run environment and artifacts (see design.md "Run environment", "Build artifacts", "Scope")
- Run environment tests still missing: a program that opens a socket and one that calls `system()` (link error); `HOME`, `/tmp`, arguments and `cin` are covered.
- Artifact location: verify how github.dev, vscode.dev/github and other virtual providers report `isWritableFileSystem`; say so before the browser's local-folder permission prompt, turn a cancelled prompt (`SecurityError`) into a clear message, offer to add `.vscwclang/` to `.gitignore`, and consider a dedicated setting to override the location. Unit-tested policy only; the extension-storage fallback is exercised by output-outside-workspace, not by a real virtual folder.
- `mmap` write-back. Cause: wasi-libc `libc-bottom-half/mman/mman.c` (the opt-in `-D_WASI_EMULATED_MMAN` / `-lwasi-emulated-mman` emulation) mallocs a buffer, fills it with `pread`, treats `MAP_SHARED` like `MAP_PRIVATE`, and `munmap` frees without writing back; WASI preview 1 has no real mmap, and wasm-wasi-core never sees it. Fixes in the sysroot we build, in order of effort: (1) make file-backed `MAP_SHARED` + `PROT_WRITE` fail loudly (`EINVAL`/`ENOTSUP`); (2) track writable shared mappings and `pwrite` them back on `munmap`, on a new `msync` (currently a link error), and at exit via `atexit` (programs often never unmap); (3) send either upstream to wasi-libc. V3 idea (write detection): wasm has no page-protection or fault hooks, so detection means either a write-back thread that periodically diffs each mapped region against a shadow copy (needs a threaded, shared-memory build and costs O(mapped size) per scan) or compile-time store instrumentation (heavy); explicit write-back at `munmap`/`msync`/exit covers most simple "mmap as file I/O" code at far lower cost, and loses only the mmap speed advantage, which does not matter for small prototypes.
- Processes (unscheduled; only after the north star is met): WASI preview 1 has no process API, so `posix_spawn`/`exec`-style launching needs a custom host import, which means the V2 Worker host (it already needs a spawn hook for `cc1`/`wasm-ld`). `fork()` cannot be "clone memory and continue": the wasm call stack is not in linear memory, so it needs an Asyncify-style transform or stack switching; the usual `fork` then `exec` idiom could instead be mapped to spawn at the libc level. `system`/`popen` also need a shell and commands as wasm programs plus pipes (a mini userland, e.g. busybox-class); Microsoft's vscode-wasm repo has an early WebShell experiment (unverified) as a starting point. Rough estimate: spawn is moderate, shell plus userland is large, `fork` is research.

- V3 idea: clangd (completion, go-to-definition, hover, diagnostics as you type) running as wasm behind a language client, filling the third of cpptools' three roles (design.md "Scope"). **`clangd.wasm` now compiles (2026-10-08, `llvm-project` fork), single-threaded**, at `llvm-project/build-single-threaded/bin/clangd.wasm`. 102 file-fed/streaming tests pass as of 2026-10-08 (including 3 crashes streaming tests found that file-fed tests missed: a `std::async` thread spawn, a `JSONTransport` double-advance, and a Windows pipe `fd_read` corruption). This repo's job is still to host it (the V1 `wasm-wasi-core` host, per the findings below) and wire up a language client.
- **Real-host clangd smoke test: passing (2026-10-09), `src/web/test/suite/clangd.test.ts`.** Drives a clangd.wasm session over `wasm-wasi-core`'s `pipeIn`/`pipeOut` `WasmProcess.stdin`/`stdout` (a long-lived `run()` with concurrent bidirectional traffic, unlike `build()`'s run-to-completion model), covering initialize/shutdown, diagnostics, hover/go-to-definition, a large completion list (framing/chunking sanity), and — the main point — the chosen didOpen/didClose indexing mitigation: it confirmed opening then closing a file still lets another file's go-to-definition resolve into it. Needs a local, unpublished `llvm-artifacts/bin/clangd.wasm` (gitignored) or the suite skips. Host-specific fixes the test surfaced, carried into the real language client below: (1) LSP `rootUri`/file URIs must use the **guest** path (`/workspace/...`), not the host filesystem path; (2) clangd needs its own `-resource-dir=/resource` argument (separate from the per-file compile-commands flags); (3) clangd needs a writable `/tmp` mount (`vscodeFileSystem` → `GUEST_TMP`) or preamble building fails with "Could not create temporary file for PCH".
- **Minimal language client wired up (2026-10-09), `src/web/clangd/clangdClient.ts`.** Started from `extension.ts` on activation (`onLanguage:c`/`onLanguage:cpp`); this is eager by design (confirmed with the user 2026-10-09) — opening any C/C++ file downloads clangd.wasm + sysroot (~110 MB total, shared with the build toolchain cache) the same way Build/Run already do, with the existing cancellable progress notification, rather than waiting for an explicit command. Spawns clangd.wasm the same way as the smoke test (clangd.wasm is a normal manifest entry, `llvm-artifacts/dist/manifest.json`, published alongside clang.wasm/lld.wasm — not a dev-only local file), then adapts the `WasmProcess` pipes to `vscode-jsonrpc`'s `ReadableStreamMessageReader`/`WriteableStreamMessageWriter` (their `RAL.ReadableStream`/`WritableStream` shape is close enough to `WasmProcess.stdout`/`stdin` to wrap directly, no custom framing code needed) and feeds them to `vscode-languageclient/browser`'s `LanguageClient` via a `MessageTransports` factory (bypassing its `Worker`-based constructor path entirely — it accepts a plain `MessageTransports` too). `uriConverters` map host URIs to/from the guest `/workspace/...` path with the existing `toGuestPath`/`fromGuestPath` (known gap: a URI outside the workspace, e.g. a `/sysroot` header from go-to-definition, round-trips wrong — collapses to the workspace root on the way in, and `Uri.parse`'s raw guest path on the way out). Verified end-to-end by `src/web/test/suite/clangdClient.test.ts`: opening a broken `.cpp` file (with its own `compile_commands.json`) makes a real diagnostic appear in `vscode.languages.getDiagnostics`. Not done yet: the didOpen/didClose fake-indexing sweep (still just `-background-index=false` with no mitigation loop), a visible progress/status indicator, settings to disable it or point at a different clangd build, and the out-of-workspace URI gap above.
- **Toolchain store bug found and fixed while wiring this up:** `getToolchainStore()` (`toolchain.ts`) was a single module-level singleton keyed by nothing — whichever caller constructed it first "won" for the rest of the process, silently ignoring every other caller's `context`. Harmless while only test suites called it (they raced for a working directory and happened to get one), but clangd's activation-time call is the first caller in the real extension, with the real (and, under `vscode-test-web`, read-only) `context.globalStorageUri`, which then broke every other test's own toolchain downloads. Fixed by keying the cache off `context.globalStorageUri.toString()` instead of a single slot.
- **Next investigation (in the `llvm-project` fork, before any V2 host work here):** clangd was previously assumed independent of this extension's hosting decisions; it is not, once it's a real dependency for IntelliSense. Before committing effort to V2 (the Worker host with spawn hook and threading, currently justified only by the sidestepped trap-hang and unimplemented concurrent compiles/threaded wasip1), answer whether clangd forces V2:
  1. Can clangd build for `wasm32-wasip1` at all (single-thread, no fork/exec/process spawn)?
  2. Roughly how large is `clangd.wasm`, independent of hosting — does it break the existing size-cap sidestep on its own?
  3. Does clangd need real threads/spawn to be usable (its background-index worker thread), or can a single-threaded, blocking-per-request mode work acceptably in a browser IDE?
  If clangd needs threads/spawn to be usable, that's a scope-justified reason to prioritize V2. If it can run credibly single-threaded, V1 may carry it and V2 stays deferred.
- **Findings from the `llvm-project` fork session (2026-10-08): V2 is not forced.** Single-threaded clangd is expected to be straightforward to build; no major wasm blockers are expected (no shared memory or other threading oddities in the single-thread path), though some unknown small blockers are likely and will only surface by actually attempting the port. `clangd.wasm` is expected to be close to, but smaller than, `clang.wasm`; size is not a concern since binaries are already downloaded separately (design.md "Distribution"), not bundled. The one real cost of single-threaded clangd: background indexing fully blocks everything else (completion, hover, diagnostics) until it finishes, since there's no second thread to run it on. **Conclusion: proceed toward V1-hosted, single-threaded clangd; defer V2** unless the porting attempt itself turns up a hard blocker.
- **Chosen indexing mitigation (from the same session, 2026-10-08): fake background indexing via `didOpen`/`didClose`.** clangd keeps an in-memory index of files opened during the process's lifetime. Rather than relying on its real background indexer (a worker thread we don't have), the extension drives a loop that sends `textDocument/didOpen` then `didClose` for each workspace file, one at a time, using LSP clangd already supports — no clangd code changes needed. Trade-offs: slower than real background indexing (open/parse/close overhead per file); no persistence (every session reload re-walks the whole workspace from scratch); and it doesn't remove the single-thread stall, it just reframes one long stall as many small per-file ones. The actual win is that the extension's loop can pause between files and let a real user request (completion, hover) through immediately, interleaving fake-indexing with live use instead of blocking on one giant pass.
  - **Implemented (2026-10-10), `src/web/clangd/indexSweep.ts` (`IndexSweep`).** `discoverWorkspaceSources()` (the same `vscwclang.sourceGlobs`/`files.exclude` as `buildWorkspace`) feeds every source, unordered, into `enqueue`.
  - **Measured (2026-10-10, `clangd.test.ts` "fake-opening a .cpp also indexes its header's own symbols"): an "includes" priority tier is not needed.** Fake-opening a `.cpp` that `#include`s a header indexes that header's own symbols (tested with a function defined entirely inline in the header, no corresponding `.cpp` definition) well enough for go-to-definition from a *different*, never-opened `.cpp` that also includes the same header to resolve into the header. So sweeping only `discoverWorkspaceSources()` (which only enqueues `.c`/`.cc`/`.cpp`/`.cxx`, not headers) already covers header symbols transitively, as long as some source file in the sweep includes each header. Only a header with no including `.cpp` anywhere in the swept set would still be unindexed; that's a narrower gap than a full "their includes" tier and not yet addressed.
  - **Implemented (2026-10-10): a "same folder as a really-open document" priority tier.** `enqueue`/`willRealOpen` route a file into a separate `priorityQueue` (drained before the plain `queue`) when it shares a folder with a currently real-open document, tracked by a `realDirCounts` map keyed on directory, incremented/decremented as files really open/close; `willRealOpen` also promotes any already-queued same-folder file out of the plain queue. Covered by `indexSweep.test.ts` ("a file in the same folder as a really-open document jumps ahead of one queued earlier elsewhere").
  - Race handling: a file already open in a real editor (`vscode.workspace.textDocuments`) is never fake-opened. The dangerous direction is a real editor opening a file the sweep currently holds fake-open: left alone, both the sweep's `didOpen` and the language client's own real `didOpen` would reach clangd with nothing closing the fake copy first. `clangdClient.ts` wires `IndexSweep.willRealOpen` into `LanguageClientOptions.middleware.didOpen`, which runs synchronously *before* the client sends its own notification, so the handoff (close fake copy, mark the uri as really-owned) happens deterministically before the real `didOpen` goes out — not left to listener registration order. All ownership reads/writes happen with no `await` between them, so they stay atomic on the single JS thread even though the sends around them are async. Covered by `src/web/test/suite/indexSweep.test.ts` (browser suite): the fake-open-then-real-open race produces exactly one open and one close, and an already-open file is never fake-opened.
  - **Fixed (2026-10-10): the loop was one-shot.** `runLoop` returned as soon as the queue drained once, so nothing re-invoked it; `enqueue` and the re-queue-on-real-close path had nothing processing them from that point on (a real bug caught before the tiering work below could be built on top of it). `wake()` now restarts the loop from `enqueue`/`onRealClose` if it isn't already running. Covered by `indexSweep.test.ts` ("enqueue after the loop has gone idle is still processed"). Re-queuing itself (so a file is indexed again after its real editor tab closes) is wired but not separately tested: under `vscode-test-web`, closing the only editor for an `openTextDocument`-opened file did not reliably fire `onDidCloseTextDocument` within a reasonable test timeout (tried `closeActiveEditor` and `closeAllEditors`, polled 8s) — an environment-timing issue, not a sign the code is wrong, so the test was dropped rather than left flaky.
  - **Implemented (2026-10-10): config tier, status bar progress, settings.** `configuredSources` (projectModel.ts) gives the files named by the default build task and each launch config's task; `enqueue(uris, 'config')` puts them in a `configQueue` drained before the other tiers (moving them up if already queued). `onDidChangeProgress` drives a `$(sync~spin) Indexing n/m` status bar item (hidden when idle). Settings `vscwclang.indexing.enabled` (live toggle), `.pauseMs`, `.holdOpenMs`. Covered by `projectModel.node.test.ts` and `indexSweep.test.ts`.
  - **Open (found 2026-10-11): verify clangd on a real vscode.dev project (e.g. `MarkovHuffman`) after the host-uri, non-source-document and `fallbackFlags` fixes.** Check: Problems stay clean for standard-library code; go-to-definition across files; status bar progress finishes and hides; defaults `pauseMs` 200 / `holdOpenMs` 300 feel right; whether the `tasks.json`/`launch.json` tier visibly helps.
  - **Open: language mode for fallback flags.** clangd gets no `-std` and treats `.h` as C, so a C++ header with no compile command may show false errors; consider a default `-std`/`-x c++-header` for headers, or deriving from `vscwclang.flags`.
  - **Open: overlap with Anycode** (`ms-vscode.anycode`, vscode.dev's built-in lightweight language support), whose symbols/definitions may duplicate clangd's; check for duplicate results.
  - **Open: sweep gaps.** A header included by no swept source is never indexed; the re-queue-on-real-close path has no test (see the "loop was one-shot" note); no persistence, so every session re-walks the workspace.
  - **Considered and discarded: a UI-to-sweep "back off" signal.** clangd's `-sync` mode has no request priority/preemption (checked `TUScheduler.cpp` in the `llvm-project` fork: no such concept), so a real hover/completion request is always stuck behind whatever the sweep already sent, with no way for either side to jump the queue once a message is in flight. Today's bound on that wait is already just one fake-indexed file (the sweep is strictly one-file-at-a-time with a pause between), which is small. A tighter bound — the extension tracking outstanding real LSP requests (e.g. via `LanguageClientOptions.middleware`) and having `IndexSweep` hold off sending its next file while one is outstanding — would shave that further, but adds coupling between the sweep and the client's request plumbing to fix a short, self-resolving stall. Not worth it given V2's real worker threads are expected to remove the underlying single-thread contention anyway (see "V2 is not forced" above); revisit only if V2 keeps slipping.
- CMake/Make/Bazel/Meson support: **Plan A (decided), not started** — a separate extension that drives those build systems and feeds this one (and clangd, once it exists) via `compile_commands.json`, which this extension already reads (design.md "Project model and integration"). **Plan B (fallback only)** is a reasonable CMake subset implemented directly in this extension, only if Plan A proves impractical.

- **C++ exceptions and `-flto` in user builds.** Tested with `llvm-project/wasi-tests/run_clang_eh_lto_smoketest.mjs <release-dir> --bin <bin-dir>` (single-thread; `--threads` untried). `-flto` PASSES (bitcode object, lld.wasm links and the program runs; `compile-flags.json` needs nothing extra, though the sysroot's `llvm-lto/<23.1.0-rc3>/` bitcode libs are keyed to wasi-sdk's clang version so our clang 24 never uses them). Exceptions FAIL: the sysroot's `eh` libc++abi/libunwind come from wasi-sdk 34's LLVM 23, which defines `__gxx_personality_wasm0(version, actions, ...)`, but clang 24 emits calls to `__gxx_wasm_personality_v0(void* exception_ptr)` (new name and ABI, `libcxxabi/src/cxa_personality.cpp:1116`), so linking fails with an undefined symbol (a forwarding shim links but traps at runtime). Mismatch audit (2026-10-11, `git diff llvmorg-23.1.0-rc3 HEAD` over libunwind, libcxxabi, libcxx include+src, compiler-rt builtins, clang CodeGen, and the WebAssembly backend's runtime-facing names): the wasm EH personality/landing-pad change (`__gxx_personality_wasm0` + libunwind's `_Unwind_CallPersonality` replaced by compiler-emitted calls to `__gxx_wasm_personality_v0(void*)`; `__wasm_lpad_context` unchanged) is the only compiler<->runtime ABI break found. Fix: rebuild libc++/libc++abi/libunwind `eh` variants with this repo's clang for wasip1 and wasip1-threads, replace them in the sysroot, then decide how users select them (setting, or extra variants in `compile-flags.json`: swap `noeh` -> `eh`, drop `-fno-exceptions`, add `-fwasm-exceptions` and `-lunwind`). Until then the `eh/` files in `sysroot.zip` are unusable with our clang; keep them only if the rebuild will replace them in place.
