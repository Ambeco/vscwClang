## Guest filesystem layout (decide before more mounts are added; see design.md "Three environments")
Open design questions, none decided. Analyze each answer against the extension host, the tool guests and the user-program guests separately.
- One emulated filesystem shared by tools and user programs (different cwd, maybe different permissions) versus today's separate mount tables. Sharing is simpler and removes drift; separate tables are safer for the compiler.
- Where the project lives: today `/workspace`. Candidate: `/home/shared/src/<project>` as the tools' cwd, with intermediate files in `/tmp` and outputs in `./build`, versus the user program starting in `~` (`/home/vscw`) and able to read (and maybe write) the source tree. Check what Make/CMake defaults and `compile_commands.json` path mapping (`hostToGuest`) assume before moving anything; `/workspace` is baked into diagnostics, the problem matcher, `guestPaths.ts`, the abort shim's `chdir` and the debug adapter.
- How much of a *nix tree to fake: `/dev/null`, `/dev/urandom` and `/tmp` are cheap; `/etc`, `/usr` and `/proc` invite subtle differences. Default to `ENOENT` for the rest, and decide whether a read-only `/etc` with a few files (passwd, localtime) is worth it.
- Whether user-program writes to the source tree should be allowed, or a per-run overlay used.
- Re-check the CPython/Make list in design.md whenever a layout decision lands: prefer the option that moves toward compatibility, and if one proves infeasible, record the abandonment (and why) in design.md.

## Milestone 1: compile in the browser
- **Priority: incremental build+test speed (decided 2026-10-27); cold full-build speed does not matter.** Remaining order: (1) measure link time with many objects (`wasm-ld` has no `--incremental`) and Run startup; (2) concurrent compiles last, since an incremental build usually has one changed file.
- Browser build latency (profiled 2026-11-09, Lua, `documents/perf_baseline.md` "Incremental build in the browser"): the first build of a page session pays about 9 s in the first `clang.wasm` use (the abort shim) before any source compiles, since `WebAssembly.compile` of the 52 MB module is not cached across page loads; try `compileStreaming` over a Cache API response (V8 code cache; IndexedDB `WebAssembly.Module` storage no longer exists in Chrome) and confirm by timing `WebAssembly.compile` alone.
  - An unchanged-tree build still costs ~0.6 s and a one-file edit ~2.2 s for ~0.7 s of compile + 0.35 s link: reading and hashing every source and header, and the per-build index; look at the per-phase `build phases` line in the `vscwclang` output.
  - Build and Run startup (build done to first output line) and fmt-sized builds are not yet measured in the browser; the fmt `format-test` target cannot be built through the CMake picker (see the Make item).
- Build cache follow-ups: verify on real vscode.dev that Cache API entries survive a tab reload and a browser restart, and the real quota (test-web showed ~3.2 GB; `navigator.storage.persist()` is not requested); a size/age readout and low-storage warning; `compile_commands.json` builds with many entries are unmeasured; a negative cache for sources that fail to compile (their errors are recomputed each build).
- Spawn hook for `cc1`/`wasm-ld` (compiles run `-fintegrated-cc1` today) and `$COLUMNS`.
- Threaded user programs: measure the cost of the threads slice on small programs (startup, memory reserve) now that it is the default; the `wasi_threaded_io` shim sends file I/O to one thread, so heavy file I/O from threads is slow and unmeasured.
- Cancel: terminate the Worker, then call `RunInterruptHandlers()`/`CleanupOnSignal()` from JS to remove temp files.
- Source selection: the Build command links every matching file into one program; `vscwclang.sourceGlobs`/`files.exclude` (defaults skip IDE scratch and build dirs) are the only control. Consider a project-file or per-target selection (a `tasks.json` schema for named targets) and a prompt when several files define `main`.
- Build still lets wasm-ld write the final `.wasm` directly (workspace or `/out` mount); consider routing it through memory (check `wasm-ld -o -`) and writing it from the host. Objects live in memory only (a persistent on-disk object cache is the Persistent build cache item above; other stores to evaluate: OPFS, IndexedDB, CacheStorage; localStorage is too small).
- Linker messages name the in-memory object (`/obj/0-x.cpp.o: undefined symbol: f()`); map it back to the source file. wasm-ld `>>>` detail lines only appeared in the hand-written parser tests, not in real output (no debug info in release mode).

## Run environment and artifacts (see design.md "Run environment", "Build artifacts", "Scope")
- Run environment tests still missing: a program that opens a socket and one that calls `system()` (link error); `HOME`, `/tmp`, arguments and `cin` are covered.
- Artifact location: verify how github.dev, vscode.dev/github and other virtual providers report `isWritableFileSystem`; say so before the browser's local-folder permission prompt, turn a cancelled prompt (`SecurityError`) into a clear message, offer to add `.vscwclang/` to `.gitignore`, and consider a dedicated setting to override the location. Unit-tested policy only; the extension-storage fallback is exercised by output-outside-workspace, not by a real virtual folder.
- `mmap` write-back. Cause: wasi-libc `libc-bottom-half/mman/mman.c` (the opt-in `-D_WASI_EMULATED_MMAN` / `-lwasi-emulated-mman` emulation) mallocs a buffer, fills it with `pread`, treats `MAP_SHARED` like `MAP_PRIVATE`, and `munmap` frees without writing back; WASI preview 1 has no real mmap, and wasm-wasi-core never sees it. Fixes in the sysroot we build, in order of effort: (1) make file-backed `MAP_SHARED` + `PROT_WRITE` fail loudly (`EINVAL`/`ENOTSUP`); (2) track writable shared mappings and `pwrite` them back on `munmap`, on a new `msync` (currently a link error), and at exit via `atexit` (programs often never unmap); (3) send either upstream to wasi-libc. V3 idea (write detection): wasm has no page-protection or fault hooks, so detection means either a write-back thread that periodically diffs each mapped region against a shadow copy (needs a threaded, shared-memory build and costs O(mapped size) per scan) or compile-time store instrumentation (heavy); explicit write-back at `munmap`/`msync`/exit covers most simple "mmap as file I/O" code at far lower cost, and loses only the mmap speed advantage, which does not matter for small prototypes.
- Processes (unscheduled; only after the north star is met): WASI preview 1 has no process API, so `posix_spawn`/`exec`-style launching needs a custom host import, which means the V2 Worker host (it already needs a spawn hook for `cc1`/`wasm-ld`). `fork()` cannot be "clone memory and continue": the wasm call stack is not in linear memory, so it needs an Asyncify-style transform or stack switching; the usual `fork` then `exec` idiom could instead be mapped to spawn at the libc level. `system`/`popen` also need a shell and commands as wasm programs plus pipes (a mini userland, e.g. busybox-class); Microsoft's vscode-wasm repo has an early WebShell experiment (unverified) as a starting point. Rough estimate: spawn is moderate, shell plus userland is large, `fork` is research.
- Dynamic linking (far future, after Make support and V2): compile and load extra wasm modules at run time. The host would inject helper imports, as it does for spawn, and the main binary would link helper stubs that call them. Make support is a prerequisite, since it is what would trigger building shared modules. `llvm-ar`/static libraries need no host work (`wasm-ld` already links `.a` files).

## Long-term wishlist
- "Suggestions" output pane with static-analysis style findings (needs a design pass against design.md "Scope" first):
  - Compiler flags that improve incremental compile time (PCH, `-fpch-instantiate-templates`, optimization level for edit-run loops), driven by measured `compiled ... in N ms` lines or `-ftime-trace`.
  - `extern template` suggestions for templates instantiated by several translation units (aggregate `-ftime-trace` instantiation events across TUs; clang has no built-in cross-TU report).
  - "Simple" function whose codegen keeps an alternate path for an edge case: suggest `__builtin_assume` / `[[assume(expr)]]`, or an explicit comment affirming the path is needed. Nothing in clang reports this directly; closest are `-Rpass-missed`/`-Rpass-analysis` remarks, which need optimized builds.
  - `switch` over an enum covering at least half the enumerators with no `default` (partly covered by `-Wswitch`, `-Wswitch-default`, clang-tidy `hicpp-multiway-paths-covered`).
  - Evaluate exposing the Clang Static Analyzer (`clang --analyze`, SARIF/plist output); see the `CLANG_ENABLE_STATIC_ANALYZER` size item under "Distribution work".
- Source-to-assembly view: after a successful compile, select lines or a function and press a button; each statement/expression gets a background color in the editor, and a side panel shows the matching assembly with the same colors. Likely route: `-g` line+column tables (clang emits column info by default) mapped to the disassembly (`llvm-objdump -d -l` or `-S` output), with `-O0` giving clean mapping and optimized builds needing "interleaved/missing" handling. Check that the toolchain ships `llvm-objdump` and that column-level granularity is reliable.
- Adaptive `vscwclang.parallelCompiles` (`0` = auto-tune beyond the fixed cap of 4). Browsers expose no host CPU/RAM, so combine signals that work everywhere: (1) hill-climb on throughput (files/s): add a worker while it improves, back off on a plateau or a wasm-grow `RangeError`; (2) per-compile peak memory (`memory.buffer.byteLength` at the end of each compile; we instantiate the module, so no `grow` patching) against a budget, with `navigator.deviceMemory` (Chromium only, capped at 8) as an optional ceiling; (3) a brake on sustained (~500 ms) slowdown versus a pre-build baseline: Worker-side `MessageChannel`/`setTimeout(0)` latency, optionally also `requestAnimationFrame` frame rate from a visible webview (rAF stops in hidden tabs; background Workers may be deprioritized or throttled, unverified). A whole-process OOM kills the tab uncatchably, so stay conservative. Chromium-only extras (Compute Pressure, `measureUserAgentSpecificMemory`, which needs cross-origin isolation) are optional. Also add `--j auto` to `scripts/perf-bench.mjs` (Node: `os.loadavg()`, `os.freemem()`).
