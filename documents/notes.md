- 2026-10-07: root cause of vscode-wasm#303 (read in wasm-wasi-core 1.0.2 `dist/web/mainWorker.js`): `handleMessage` runs `instance.exports._start()` inside an async handler wired as `.catch(console.error)`; a trap (`RuntimeError: unreachable` from `assert`/`abort()`/`__builtin_trap`, or out-of-bounds, div by zero, stack overflow) is only logged in the worker, `_done` never resolves, `main()` never posts `workerDone`, so the host's `run()` never settles. Only `proc_exit` (host call, resolves run with the code) and a normal return from `_start` (workerDone, resolves 0) end a run; `terminate()` also resolves 0, so Ctrl+C prints a misleading `exited with code 0`. The worker is private to wasm-wasi-core, so the extension cannot hook it. Verified under Node WASI: a user-level `extern "C" void abort() { __wasi_proc_exit(134); }` turns an assert failure into exit 134; direct traps stay traps. A proper fix is a try/catch around `_start()` upstream (or our own V2 host).
