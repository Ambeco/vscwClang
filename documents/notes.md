# Notes

History and gotchas worth remembering; design lives in `design.md` and `design_*.md`. Entries are dated by when learned.

## Environment and test harness
- Desktop VS Code cannot run this extension (2026-10-06): `ms-vscode.wasm-wasi-core` was loaded in the Node host while ours is browser-only, and cross-host dependencies are refused. Test via test-web or vscode.dev. `engines.vscode` is ^1.90.
- `npm test` needs `--coi`, a workspace folder arg (`src/web/test/fixtures/workspace`) and port 3000 free; a stale `vscode-test-web` on 3000 (`EADDRINUSE`) makes the suite run against old state. `*.node.test.ts` are excluded from the browser bundle in `esbuild.js`. `pretest` reads `llvm-artifacts/MANIFEST`; with a hand-made dist run `npm run compile-web` and `vscode-test-web` directly (the test server does not follow directory junctions). `mochaTestRunner.ts` logs each failure as `[test] FAILED: ...`, popups and slow UI calls with timestamps.
- Test-web facts: `getConfiguration('tasks'|'launch')` returns parsed JSONC; `tasks.fetchTasks` does not list configured tasks and `tasks.executeTask` needs `execution`, so the cppbuild test calls the provider's `resolveTask`; task problem markers carry a `vscode-remote:` scheme (match by path); `findFiles` with a `node_modules` exclude still returned them (extra filter in `extension.ts`); two `LanguageClient`s in one host collide on command ids (the test workspace turns the activation client off).
- `workbench.action.tasks.build`/`runTask` (Ctrl+Shift+B) are silent no-ops in the web workbench (test-web and vscode.dev): they wait for a terminal backend a pty-less web workbench never has (2026-10-22, found by patching the cached workbench bundle and running `vscode-test-web --verbose`). `tasks.executeTask` is unaffected. Not fixable here.
- Live vscode.dev is scripted (`scripts/live-driver.cjs`, `scripts/serve-dist.cjs`, `documents/live_testing.md`). The driver runs from memory: restart it after editing. vscode.dev opens the OPFS folder as an untitled multi-root workspace, so workspace settings live in `default.code-workspace`; the live profile's User setting `loggingLevel: Debug` made json.hpp "stall" (a folder-level `Error` did not override it), so `live-flow-project.sh` writes the User setting first. The browser FS has no watcher: close all editors before re-seeding. Page console is forwarded by test-web only with `--verbose`. A page hung with `Runtime.evaluate` unanswered needs Chrome restarted; `Profiler.start` over worker targets works only for busy workers.
- `build.log` ends with a `--- timings ---` block (per-source `compiled ... ms`, phase line) so flows need not read the Output channel.
- Git Bash: `/tmp` is not the `C:/tmp` Node resolves (`cygpath -m`); a `/`-leading `--only` regex is path-converted; launching a `.bat`: `cmd //c x.bat` and `cmd /c x.bat` failed, `Start-Process cmd.exe /c <absolute path> -WorkingDirectory <dir>` worked. A killed Node harness run leaves a `clang-wasi-*` dir in `%TEMP%`.
- Do not `taskkill /IM node.exe` to stop a hung test. `npm run test-node` hangs if a test leaves a worker or timer alive (mocha runs without `--exit`).
- Compat survey clones live in `C:\Users\mooin\vsclang-compat` (114 MB, outside the repo); gotchas: `doctest.h` treats `__wasi__` as no-exceptions.

## Toolchain build and publishing
- Size pass (2026-10-11): the `name` section was 32-41% of every binary; `scripts/strip-wasm.mjs` drops it and `.debug_*` (clang 108 to 63 MiB). Stripped binaries trap with function indices, not names (unstripped copies were kept locally). `LLD_WASM_ONLY=ON` saved only ~4 MiB. `CLANG_ENABLE_STATIC_ANALYZER=ON` kept on purpose (an `--analyze` command is plausible). `wasm-opt -Oz` and LTO were not tried.
- `llvm-artifacts/resource` is the flattened resource dir (contents of `resource/lib/clang/<ver>/`); `package_release.mjs` nests it and `make-toolchain-dist.mjs` flattens it. A nested copy gives `cannot open /resource/lib/.../libclang_rt.builtins.a` and `'stddef.h' file not found`.
- Publishing: `make-toolchain-dist.mjs --llvm <staging>` re-zips with new timestamps, so every chunk hash changes even for identical content; publish only the changed zips plus a merged manifest (hash recomputed, pin set by hand), as in v24.0.11 (clangd), v24.0.12 (`llvm-ar`) and v24.0.13 (clang, PCHs, `compile-flags.json`). Staging holds the PGO binaries from `C:\Users\mooin\pgo\variants\keep`; `build-clangd-threads.bat` is MinSizeRel and must never be published.
- PCHs embed the compiler's git revision, so any new `clang.wasm` needs regenerated PCHs; a clang from another commit rejects the benchmark's prebuilt PCH and silently fails every C++ unit. A Visual Studio update breaks the native tree's `cmake_pch.hxx.pch` (delete and rebuild). The fork's `/build*` gitignore hides `build-*.bat`.
- jsDelivr (2026-11-08): the tag listing API answers 403 "Package size exceeded 50 MB" for every tag, but per-file URLs work; the first request after a new tag can still 403 and succeed on retry, so warm and hash-check every chunk after publishing.
- Fixtures: `build-debug-fixtures.mjs --release <llvm-project>/release/<tag>` (rerun after editing `debugStub.c`; needs the fork's `build/` tools), `build-host-fixtures.mjs` likewise; the release's resource dir is nested and the script flattens it. Single-threaded builds are retired, so `perf-wasmer.mjs` (needs a no-threads `clang.wasm`) cannot run.
- The debug-coverage guard flags (`-mllvm -sanitizer-coverage-stmt`, `-sanitizer-coverage-spill-debug-vars`) are `cl::opt`s in the fork's `SanitizerCoverage.cpp` (relink ~11-20 s via `cmake --build build --target clang`). The published `compile-flags.json` of some early releases lacks `debugCoverage`, so debug builds from them get block guards only. A wasm-EH fix (sancov guard calls in catch/cleanup pads need the `funclet` bundle) shipped in v24.0.13.

## Host and WASI
- Worker rules and the sync channel are in `design_host.md`. Probe results: a Worker that creates a child Worker then blocks in `Atomics.wait` never sees the child start (Chromium), so the extension host creates all Workers.
- Constant inode in `filestat` broke only clang's include search (`'cstdio' file not found`): clang dedupes include dirs by inode. Reproduce clang under `GuestProcess` in node by bundling `guestWorker` with esbuild as `guestProcess.node.test.ts` does.
- A wasm `catch_all` (in `std::terminate`) swallows the `proc_exit` exception, so `GuestWasi` keeps the first `proc_exit` code whatever ends `_start`. Reading the uncaught exception type from the escaped `WebAssembly.Exception` was rejected (needs the `__cpp_exception` tag exported and libc++abi's header layout); the `--wrap=__main_void` shim is used. Wrapping `__main_argc_argv` or `__original_main` misses one `main` form.
- Shared-memory views break browser APIs: `TextDecoder.decode` and `crypto.getRandomValues` throw on a SharedArrayBuffer view (node accepts both), so copy with `slice` first.
- `vscode-jsonrpc` writes the LSP header as a string, so the stdin facade must accept strings. A `failed` outcome rejects `run()`; `clangdClient` has no rejection handler, so check the log when the client hangs.
- wasi-libc `isatty` needs a character device without `FD_SEEK`/`FD_TELL` rights, otherwise stdout is fully buffered after the first flush (first line, stderr, then the rest at exit). User programs set `GuestOptions.terminal`; tools do not.
- Build on the Worker host (2026-10-26): per tool call Worker boot ~8 ms, instantiate 6-8 ms (clang), first build adds ~0.4 s `WebAssembly.compile`. Decision: no warm Worker pool (saves under 1% of any real file); revisit if concurrent compiles start many Workers at once.
- clang `-o file` into the local-folder FS hung on vscode.dev (2026-10-06, a 15 KB `.o.tmp` left); fixed by `-o -` into an in-memory `/obj`. First workspace write needs a user gesture, so it precedes the toolchain download.
- Threaded lldb reactor aborts if `thread-spawn` fails; `ReactorHost` gives it a separate spawner Worker whose children get no extension-host channel and only a shared read-only copy of the target file (with empty fd tables the target silently failed: `0x76 is not in any loaded module`). A failure in a thread is invisible while main blocks: relay child errors and trace with `fs.writeSync(2, ...)`.

## Compile speed findings
- Cost is libc++ header parsing, not the file's own code (2026-10-06/27): `<iostream>` ~1.2 s, whole real files 2.5-5 s; Frontend dominates (`-ftime-trace`), Backend ~10%. `node --cpu-prof` on unstripped `clang.wasm` is flat (host side ~20%: WASI I/O 9%, `path_readlink` is the largest call). `-std=c++23` costs ~2x c++17 (ranges/concepts headers).
- `clang.wasm` is NOT slower than native wasm32 clang (wasi-sdk 34): 2.5/2.7/5.1 s vs 2.7/2.9/5.4 s on the Markov files. Browser is about as fast as Node. A repeat compile is ~25% faster than the first (tier-up), so keep the compiled Module alive. `-ftime-report` is ~10x slower in the browser (clock reads): use `compiled ... in N ms` lines.
- PCH: `-include-pch` took `Main.cpp` 2.5 to 1.06 s under Node; `-fpch-instantiate-templates` adds ~5-10%. A PCH build in the threaded clang is no faster than single-threaded and a PCH compile spawns no threads. Implicit modules FAIL on our sysroot (libc++'s modulemap redefines `wchar.h` functions; wasi-libc has no module map). `wasm-ld` rejects `--incremental` and `--gdb-index`; `-fuse-ld=lld` is a no-op. Clang errors on PCH/flag mismatches (`-std`, `-O`, exceptions/rtti, `-fPIC`, sanitizers) but silently accepts extra `-D`/`-U`; the PCH needs a sysroot copy with mtime 0 plus `-fvalidate-ast-input-files-content`; C headers in the PCH make user globals like `y1`, `rand`, `time` clash (hence the retry).
- Failed experiments: PGO retrain with `--debug` compiles gave no debug-build gain (82.4 vs 83.7 s corpus); holding inlay hints, semantic tokens and other requests until clangd's first diagnostic changed nothing (5.8 vs 5.7 s); matching clangd's fallback command shape did not stop preamble rebuilds on config changes.
- clangd preamble (Node, 2026-11-16): `-Xclang -skip-function-bodies` leaves the preamble unchanged (clangd already skips bodies there); `-pch-storage=memory` is neutral under Node; preamble is declaration/template-parse bound. An unsaved header edit rebuilds nothing; a saved one rebuilds the dependent's preamble in ~65% of the first. `perf-clangd-edit.mjs` needs a `/tmp` preopen or every preamble fails; `PERF_STDERR_FILE` in `clang-wasi.mjs` keeps clangd's stderr when the guest will not exit.
- clangd rebuilds the preamble of every open file named in a `workspace/didChangeConfiguration` compile-database change, even with an identical command, so the background-index overlay skips open files and sends them on close.
- clang-tidy adds no measurable index cost (it runs only on open files); the shipped clangd has `CLANGD_TIDY_CHECKS=ON` since v24.0.11. `clangd --check` prints no warnings, so probe tidy over LSP with `-sync`. `modernize-use-nullptr` arrives as a severity-4 hint (tidySeverity.ts raises it). clangd logs `E Failed to auto-detect resource directory` at startup despite `-resource-dir`: benign. Header insertion on completion needs `#pragma once`/guards in the header. An occasional Node-harness run starts empty (no diagnostics): rerun.
- clangd start-up "sources" cost (0.75-1.1 s) was `createDirectory` on a `clangd-tmp` folder holding leaked preamble files (`staleTempFiles.ts`, 10-minute age limit for other tabs). Running the toolchain load and workspace scan in parallel made start-up slower (single extension-host thread). The Output channel loses most of clangd's stderr under load: treat missing lines as a capture gap.
- clangd has no dedicated file-I/O thread (no `wasi_threaded_io` shim in the shipped `clangd.wasm`); `CachingGuestFs`/`RpcStats` share reads and count requests. A threaded clangd shipped 2026-10-30; a single-threaded pin is rejected by `startClangdClient`, and background indexing sees only files with compile commands.

## Debugger
- `wasmScan` must handle the legacy `try` opcode (`try_table` 0x1f is unhandled). At `-O0` the frame-base local is set with `local.set` after `global.get sp; i32.const N; i32.sub`. Wasm name of `main` is `__original_main`. The reactor runs on `@bjorn3/browser_wasi_shim` (ESM-only: tsconfig uses `module: ES2022`, `moduleResolution: Bundler`; pass `{ debug: false }`).
- sancov prunes blocks by default (Debug uses `no-prune`) and the backend can place a block's first instructions before its hook call, so a line maps to the first guard at or after its first address when no other line's code lies between, else the last before it.
- Locals check (2026-10-27): every `DW_OP_fbreg` variable decoded correctly; the failures were wasm-local variables (struct by value, VLA pointer), fixed by the spill-debug-vars flag, and the frame-base local choice for VLA functions. Open sibling-call gap is in `remaining_work.md`.
- Conditions, hit counts and logpoints are decided in `DebugController` at the stop, so a hot conditional breakpoint costs a round trip per hit; the reactor has no expression evaluator (`debugExpression.ts`).
- Pause and live breakpoint edits write guard bits and a pause word straight into the program's shared memory (threaded builds only); keep both paths working when changing the stub or `StubDebuggee`.
- All-stop and trap stops were built on the stub and shared memory, not a custom runner (`design.md` "Alternatives considered"). Stops must be served FIFO (a ticket lock) and a resume must wait for parked threads to wake, or a thread re-hitting its breakpoint starves the others (a mutex did). wasi-libc has no `gettid`, so a trapped thread is found by its exported `__stack_pointer`. Rebuild the fixtures after any stub change.
- Live-checked on vscode.dev (2026-11-08/15): throw/catch, multi-file stepping, divide-by-zero, failed `assert`, a trap in a thread with main in `join`. Pause while blocked in `cin` takes effect only after input (the Debug Console says so).

## Wasmer and Make
- Wasmer SDK 0.19.1 (2026-11-04/05): clang runs unmodified; compile of an `<iostream>` file 1.2 s vs ours 1.4 s, but `packages.load(clang.wasm)` takes 4.1 s (ours: 0.15 s) and the sandbox accepts only `/workspace` paths, in memory. `Command.run()` throws on nonzero exit unless `check: false`; a trap rejects `wait` with `RuntimeError: js: ...`. The SDK has no `Directory.fromBrowser`, `mounts` option or OPFS support; the only mount hook is an undocumented "iOS prototype" bridge (`mountHost`/`__wasmerHostFileSystem`) that `Sandboxes.create` never calls. `npm run check-types` covers only `src` because staged SDK `.d.ts` files failed it. Spike and licensing: `build_systems_feasibility.md`; VS Code's `Worker` patch wraps URLs in `importScripts`, fixed by a classic-`import()` blob subclass.
- make.wasm spike (GNU make 4.4.1, route M1, 2026-11-16) passed, built under node:wasi from a hand-written `config.h`, gnulib `glob.h`/`fnmatch.h`, ~15 ENOSYS stubs, `ST_MTIM_NSEC=st_mtim.tv_nsec`, `dir.c` `sizeof(d->d_name)` patched to 0 (WASI's `d_name` is flexible) and `main` cut to two parameters (wasm-ld's `main` rename applies only to `(argc,argv)`). `node:wasi` cannot run it on a real directory (`fd_readdir` is ENOSYS); `GuestWasi` can. `scripts/build-make-wasm.mjs` now reproduces it (stripped 272 KB, deterministic zip, same dry-run output as the spike on the fixture Makefile; under Git Bash set `MSYS_NO_PATHCONV=1` or `-C /workspace` is rewritten).
- Build graph (2026-11-16): checked end to end in the browser suite with a captured trace. With no `hostRoot`, `parseMakeTrace` takes the first top-level `Entering directory` as root; pass `'/workspace'` for guest runs. `make -n` without `-B` omits up-to-date targets (lowering then fails on a missing object). The wasm make expands `$(shell)` to nothing and only warns, so the classifier is not run on such Makefiles.
- Idea (2026-10-07, out of scope here): a make-reading extension could implement its own subset dialect instead of porting GNU make.

## Other
- Sources that do not compile for wasm32 (2026-10-06 survey of old MPD code): `windows.h`/`winsock2.h`, MSVC functions (`_stricmp`, `strcpy_s`), exceptions disabled, MSVC-permissive templates, 64-bit layout assumptions (wasm32 pointers are 32-bit). Library survey: `compat_survey.md`.
- Formatting is clangd's built-in clang-format; `.clang-format` is read live through the workspace mount. cpptools' `C_Cpp.formatting` enum is `clangFormat|vcFormat|default|disabled`, default `default`.
- The extension's generated clangd `config.yaml` works over LSP (fragments by language, `.h` as C++20, `-header-insertion=never`); live on vscode.dev, hover and completion show no Anycode duplicates. In vscode.dev Output, `[INDEX]`/`[CONFIG]` lines are Anycode's.
- `scripts/clang-wasi.mjs` runs threaded modules (nested worker_threads); the threaded `clang.wasm` needs `-fintegrated-cc1`; `VSCWCLANG_WASI_TRACE=1` logs thread spawns and WASI call counts. Real wasm EH note: the `wasi-sdk` `eh` libs came from LLVM 23 and clash with clang 24's personality ABI; fixed by rebuilding the runtimes from the fork.
- A failed build caches no objects (a compile error recompiles that unit every build).
- Ninja reader pitfalls: a rule binding is expanded lazily and edge/file variables are stored already expanded (expanding twice loses `$$`); CMake's Windows output uses `cmd.exe /C "..."` only on link/archive rules, so compile lines still need backslash-to-slash. File API queries must be empty files named `codemodel-v2` etc. (a `query.json` in the query folder is rejected as "unknown query file").
- Real committed CMake dirs (MIT, GitHub `filename:build.ninja`) showed `gtest_discover_tests` appends `cd DIR && cmake -D TEST_TARGET=... -P GoogleTestAddTests.cmake` to the link command (Windows: inside `cmd.exe /C`, spaced cmake path); `ninjaTrace.ts` strips it with a note. Many hits are `_deps/*-subbuild` dirs or lack `CMakeFiles/rules.ninja`; check both exist before using one.
