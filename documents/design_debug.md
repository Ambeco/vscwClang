# Design: debugger

The debug stub channel and what the debugger can do. Overview: `design.md`.

## Debug stub channel
Debug builds link `src/web/debug/debugStub.c`, the program-side half of debugging, kept in the program so the host needs no custom import. It is the `__sanitizer_cov_trace_pc_guard` hook (exported by the linker so `scanProgram` finds the call sites), so the program imports only WASI functions. It keeps a shadow call stack of (guard, `__stack_pointer`) per instrumented frame, checks breakpoints by a bit in the guard word itself (no table lookup), and supports step into/over/out by comparing stack pointers. Debug builds add `-mllvm -sanitizer-coverage-stmt` (passed when `compile-flags.json` has a `debugCoverage` entry; the llvm-project fork's `SanitizerCoverage.cpp`), which puts an extra guard, calling the same hook, before the first instruction of every source line that starts inside a basic block and right after each call that has more code on its own line, so a guard exists for nearly every line and a return lands back on the call line. Stepping stops at each hook; the adapter repeats while the line and frame are unchanged. With an older toolchain (no `debugCoverage`) guards stay per block and the notes in the next paragraph about block granularity apply.

The channel is the program's own stdio. At startup the stub sends `hello` and blocks in `fd_read` until the host releases it, so breakpoints are armed before any user code runs. Stub to host: frames `ESC _ vscw <text> ESC \` inside stderr (`stop`, `mem`, `memerr`, `error`); `FrameDemux` splits them from the program's own stderr at any chunk boundary and passes other escape sequences through. Host to stub: `vscw bp|mem|go|into|over|out` text lines on stdin, read one byte at a time so nothing meant for the program is consumed. The host writes commands only while the program is stopped and forwards typed program input only while it runs (`StubDebuggee.writeInput` queues input typed at a stop and sends it right after the resume command). Input written just before a stop can still be unread, so a stub line that does not start with `vscw ` is handed back as an `input` frame (hex bytes) instead of being an error; the host puts those bytes at the head of the queue, and a resume that followed such a write first sends `vscw sync` and waits for `synced`, which guarantees every handed-back byte has arrived before the resume command and the queue go out. Memory pages (4 KiB) are read by the stub itself (bounds-checked, so a wild address reports `memerr` instead of trapping).

What the debugger can and cannot do follows from where the hook sits. The hook runs at the start of every basic block and at every line change inside one, so a line breakpoint stops exactly on its line (with block-only guards it stops at the start of the enclosing block and the `setBreakpoints` response says so), and stepping moves line to line. A stop at a function's entry guard sees parameters before they are spilled to the stack, so a step into a call goes on to the callee's first body line (`BreakpointIndex.isEntryGuard`); a breakpoint on the `{` line still stops at the entry guard. IR has no is_stmt flag, so a statement split over several lines stops on each, and a loop whose header and body share one line is one stop. Stepping off the end of a callee stops on the call line in the caller (the post-call guard); a call with nothing left on its line returns straight to the next line's guard. Debug builds pass `-fsanitize-coverage-ignorelist` (`coverageIgnorelist.ts`, written to the in-memory `/obj` mount) that excludes C++ standard-library functions by mangled name (`_ZNSt*`, `_ZSt*`, ...; a coverage ignorelist cannot match by header path), so they have no hooks and step-in never lands in them; a user specialisation of a `std` template loses its guards too. The Variables pane lists the frame's variables and expands them through the reactor's `wasm_dbg_get_variables`, which names a value by an index path (variable number, then child numbers) rather than an expression, so data-formatter children such as a `std::vector`'s elements work too and a call can be re-run after missed memory pages are fetched. A variable that lldb cannot read (a by-value struct parameter or a VLA pointer lives in a wasm local, which no host can read) is listed with the reason as its value. A function that uses a VLA or `alloca` moves `__stack_pointer` inside its frame: `scanProgram` takes the frame-base local from clang's pinned copy of the prologue's local (`local.get A; local.set B`), and `ShadowStack` keeps the frame's entry `sp` when a non-entry guard of the same function sees a lower one. The VLA itself is still unreadable (see above). Hover, Watch and the Debug Console evaluate variable paths (`x`, `p.y`, `arr[2]`) through lldb, and anything more (`a + b`, `i == 3`) with `debugExpression.ts`, a small C-like evaluator whose variable reads go through the same lldb path formatting; breakpoint conditions, hit counts (`N`, `>= N`, `% N`, counted only when the condition held) and logpoints (`{expr}` in the message) are decided by the controller at the stop: the stub stops on the guard as usual and the controller resumes at once when the verdict is not to stop (a condition that cannot be evaluated stops and says why). Threads (all-stop, with the program's shared memory): the stub keeps the shadow stack and step state per thread (`_Thread_local`) and registers each thread in a static `registry` (id, stack addresses, state) at its first hook, so the host lists every thread and reads a parked thread's shadow stack straight out of shared memory (`stubRegistry.ts`; the `hello` frame carries the registry address). A stop sets `CTL_STOPPED` in the same `control` word as the pause bit, so the per-guard cost stays one load: every other thread parks at its next hook (`memory.atomic.wait32` on a generation word), and falls through to its own breakpoint check when the world resumes, so a breakpoint it sat on still fires. Stops are served in arrival order by a ticket lock, and a resume waits briefly for the parked threads to wake before the resuming thread runs on, otherwise a breakpoint it hits again at once would starve them. A stop also waits up to 40 ms for the others to park; a thread blocked in a lock, sleep, `join` or `cin`, or in uninstrumented code, does not reach a hook and is listed as not stopped, named `[blocked or running]`, with the shadow stack it had at its last guard (read from the registry anyway; dropped if it does not map to known guards, since a thread that is really running can be mid-update); it cannot stop sooner (the same limit as Pause). Such a thread is remembered as a laggard (a stub-private byte per registry slot, cleared when it next parks) and later stops wait only about 1 ms for it, so a program whose main sits in `join` does not pay 40 ms on every internal stop (false conditions, logpoints, step repeats). Each `stop` frame names its thread (`1` is main). The controller announces every thread (DAP `thread` events, `exited` when one ends), reports `allThreadsStopped: true`, serves any thread's stack (frame ids of a thread other than the stopped one are `threadId * 65536 + index + 1`; Variables and evaluate switch the reactor to that thread's frames), resumes every thread on Continue whichever thread the client names, and steps only the thread that stopped (a step on another thread is an error that names the right one). Without shared memory (`vscwclang.threads` off) there is no all-stop: the stopped thread alone is known, announced when it first stops, and other threads' stacks are empty. Traps are stops too, in the same threaded builds: debug links export `__stack_pointer`, a thread Worker that traps reports the engine's stack trace and that thread's stack pointer with its tid, and `GuestProcess` (option `onTrap`) keeps every Worker and the shared memory alive instead of ending the process. `StubDebuggee.holdTrap` then sets `CTL_STOPPED` itself (the trapped thread never reaches the stub, so nothing else would park the others), finds the trapped thread in the registry (`trapStop.ts`: main by tid 0, another thread as the one whose outermost recorded `sp` is the lowest at or above the trapped stack pointer, else the only non-main thread still running) and reports reason `exception` with the engine's message (DAP `stopped` with `text`, plus `exceptionInfo`). Its shadow stack gets exact pcs from the stack trace: the trapping instruction on top and call sites below, matched to frames by function. Memory is read straight from the shared `WebAssembly.Memory`, since the stub is gone. The program cannot continue: Continue or any step ends it, reported as the usual trap exit (code 139 and the crash message). A failed `assert`, `std::terminate`, `abort()` and an exception uncaught in `main` end in the abort shim (linked into every build), which exits 134 through `proc_exit`, not a trap. In a debug build the shim first calls `vscw_debug_abort` (a weak reference the stub defines), which stops like a breakpoint (stub reason `abort`, reported as an `exception` stop whose message says so); the program is still alive, so Continue resumes it into the exit 134. The stack is the shadow stack up to the function that called abort, at its last guard. Only an exception thrown outside `main`, such as in a static constructor, traps instead, and it carries no wasm stack trace, so its frames are the shadow stack's. A build without shared memory has nothing to read after a trap, so it still ends the program at once; the launch notice says so. A function breakpoint arms the function's first body guard (matched on the demangled name by `demangle.ts`), and stack frames show demangled names with `main` for the compiler's `__original_main`. The cost of a conditional breakpoint in a hot loop is one stop round trip per hit. Pause and breakpoint changes while the program runs go through the program's shared memory (every threaded program has one, created by the extension host): the host sets or clears bit 0 of a guard word with `Atomics.or`/`Atomics.and`, and Pause sets the stub's `pause_requested` word (its address is the third field of `hello`), which the hook tests on each call; the first hook to see it clears it and stops with reason `pause`, and every stop clears it so a pause that raced a breakpoint does not fire again after the resume. The host owns the bits for the whole session (no `bp` command), and writes none before the start stop because the shared-memory initialisation would zero them. A Pause only lands at the next guard, so a program blocked in `std::cin`, a sleep or a lock, or running uninstrumented `std` code, stops when it next reaches one. Without shared memory (`vscwclang.threads` off) `capabilities` say so: changes are queued to the next stop and Pause fails with an explanation. Pause while stopped is a no-op. By default (launch attribute `console`: `integratedTerminal`) the program's stdin, stdout and stderr are a terminal owned by the adapter (`ProgramTerminal` over `LineEditor`: echo, Backspace, Enter; no end-of-file key in debug), so prompts sit beside the typed answer and input reaches `std::cin`; the debug stub's own stdin cannot be the terminal because it must stay a pipe for commands. With `console: internalConsole` the output goes to the Debug Console and stdin is not connected. In terminal mode `resolveLaunchConfiguration` (`launchConfiguration.ts`) defaults `internalConsoleOptions` to `neverOpen`, because VS Code otherwise raises the empty Debug Console over the program's terminal, and the Debug Console gets one line naming the terminal (`DebugTarget.notice`). It also turns an empty configuration (F5 with no launch.json) into the default launch; without that, VS Code starts nothing.

lldb reads memory synchronously but the channel is asynchronous, so `PagedMemory` serves the current stop from a page cache, recording misses; `evaluateWithMemory` fetches the missed pages and re-runs the lldb call. lldb formats a failed read into the value text instead of throwing and keeps that result for the stop, so each re-run must first call `ReactorHost.setStop` again with the same frames. Verified on Worker host pipes (`debugStub.test.ts`) and in a worker harness with blocking stdin plus the real reactor (`stubChannel.node.test.ts`).
