# Live testing on vscode.dev

How to drive the real vscode.dev with a persistent test browser, plus the findings from the first full pass
(2026-10-21) with enough context for another session to pick each one up. Fixed items are listed so they are not
re-investigated.

## Harness

- **Chrome with a dedicated profile**, never the user's: `chrome.exe --user-data-dir=%USERPROFILE%\.claude\chrome-test-profile --remote-debugging-port=9333 --no-first-run https://vscode.dev/`. Chrome 136+ refuses remote debugging on its default user-data dir, so `--profile-directory` alone cannot be automated. The profile keeps the granted permissions, the installed extension, the `vscwclang.toolchainUrl` user setting and the cached toolchain (listed in `~/.claude/temp-cache-registry.md`, keep).
- **Extension**: `npm run package-web`, `npx serve --cors -l 5000`, then palette "Developer: Install Extension from Location..." with `http://localhost:5000` (a trust popup and a "read local files" popup appear once; reinstall after a `package.json` change, reload the tab after code changes).
- **Local toolchain**: `node scripts/serve-dist.cjs llvm-artifacts/dist` (adds the CORP header COEP needs; `--slow` throttles so the Cancel button can be clicked), and user setting `{"vscwclang.toolchainUrl": "http://localhost:5001"}` (open it with palette "Preferences: Open User Settings (JSON)"; type it with `insertText`, because typing triggers bracket auto-close). The output channel says `toolchain override ... accepted without a pin`.
- **Driver**: `node scripts/live-driver.cjs`, then `curl --data-binary @test.js http://127.0.0.1:9444/run`. `seed({...files})` writes an OPFS folder, reloads and opens it through a patched `showDirectoryPicker` (no picker click, no GitHub sign-in; `vscode.dev/github/...` demands a GitHub login). `cmd('vscwClang: Build C++')` clicks the exact palette row (typing the name and pressing Enter picks the "recently used" command instead). `console.log` collects console warnings/errors, failed requests and HTTP >= 400 per `step()`.
- **Gotchas**: this opens an *untitled multi-root workspace* (`default.code-workspace`, folder `file:///proj`); workspace settings live in that file (palette "Preferences: Open Workspace Settings (JSON)"; keep `folders` when replacing it) and persist across `seed()`, so reset them between tests. F11/Shift+F11 never reach VS Code (Chrome fullscreen); click the debug toolbar instead. The terminal needs a click before it takes typed input. `Terminal` panel text is canvas, so read run output from screenshots. `p.locator(...).innerText()` waits for the default timeout when the element is missing; use `p.evaluate` for polling. Backslashes in heredoc-written JS arrive halved (write test files with the Write tool).
- **Ignorable console noise** (vscode.dev itself): `[lifecycle] Long running operations during shutdown`, `IndexedDB database 'vscode-web-db' is closed`, `Failed to execute 'abort' on 'IDBTransaction'` and `Unable to resolve resource output:tasks` (all caused by the harness reloading the page), `extension 'github.vscode-pull-request-github' wants API proposal`, `[AgentHost:remote]`, `Permissions policy violation: unload`, `[CloudSandboxApi] No 'github' session`.

## Verified working on vscode.dev (2026-10-21, local toolchain `v24.0.2`)

Everything below ran on the local, unpublished `v24.0.2` (stripped binaries, eh libs, lldb reactor), not on the pinned `v24.0.1` that users get today; re-run the pass against the published toolchain after pinning.

Multi-file Build, Build and Run, stdin echo in the terminal, quoted `Build and Run with Arguments...`, compile errors and warnings in Problems (also inside a header, with the `In file included from` context), edit/rebuild loop and Problems clearing after a fix, assert (`exited with code 134 (aborted)`), Ctrl+C (`terminated`), file I/O under `/workspace`, `HOME=/home/user` kept across reloads and `TMPDIR=/tmp`, link error for two `main`s, `vscwclang.sourceGlobs` narrowing, `vscwclang.flags` (via the workspace file) with `-pthread` dropped and forbidden flags (`--target`, `-o`) rejected with did-you-mean text, default `tasks.json` task (`-std=c++20 -DNAME=7`) plus `launch.json` args (`[x] [y z]`), `compile_commands.json` (`-DCC_VALUE=42`, after the fix below), double-triggered Build (two sequential builds), downloader (progress, Cancel: "files already downloaded are kept, so running it again resumes", offline: three retries then a CORS/internet hint, Clear downloaded toolchain, cache survives reloads and extension reinstall), try/catch exceptions, clangd hover/go-to-definition (workspace symbol)/completion/as-you-type diagnostics/`Indexing 2/6` status bar (see slowness below), Debug (F5, line breakpoint, Paused on breakpoint, call stack `sq(int)` + `__original_main`, toolbar Step Into/Over/Continue about 300 ms each, program output in the Debug Console, clean exit).

## Fixed during the pass

- `vscwclang.compileCommands.include` nested under the string setting `vscwclang.compileCommands`: VS Code ignored it (console: `Ignoring vscwclang.compileCommands.include as vscwclang.compileCommands is ""`) and `get()` returned `""`, so Build and Run threw `...get(...).map is not a function` whenever a `compile_commands.json` existed. Renamed to `vscwclang.compileCommandsInclude`; `settingsSchema.node.test.ts` fails on any setting key that is a dotted prefix of another. Verified live afterwards.
- The flag error for `--target`/`-march` suggested a `threads` setting that does not exist; it now says "to remove it".

## Open findings (most important first)

1. **Run of a debug-mode build hangs with a blank terminal.** A `tasks.json` task containing `-g` (cpptools' default template has it) builds into `.vscwclang/debug/` and Build and Run opens a terminal that stays empty for 30+ s; the same task without `-g` prints the output at once. Suspect the debug stub linked into debug builds (stdin-gated, see remaining_work "stdin is not connected"): Run should link or run without the stub. Repro: seed `main.cpp` printing a line plus `.vscode/tasks.json` with `-g` and a `cppbuild` default build task, palette Build and Run C++.
2. **clangd is very slow to become useful, and after every edit. Working as intended until V2 multithreading (decided 2026-10-21): do not optimize; revisit only after the custom runner lands.** `main.cpp` including `<iostream>`, `"model.h"` (`<map>`, `<string>`, `<vector>`): first preamble took 64 s (clangd log `Building first preamble` at 23:11:21, `indexed preamble AST` at 23:12:25), first hover about 113 s after opening the file, and after typing `m.` completion replied after about 50 s (179 ms of its own work, so it queued behind a preamble rebuild) and diagnostics after about 50 s. The same pass with only `<cstdio>` showed diagnostics after 4 s and the whole 6-file index in 6 s, so cost scales with the libc++ headers in the preamble although `clang.wasm` compiles the same `main.cpp` in 1.4 s. While it is busy hover and completion show "Loading..." with no progress indication (no status bar item before indexing starts). `-sync` mode serializes everything behind it. Debug logging was not the cause (default logging: 113 s). Hypotheses to check: preamble `.pch` writes go to `/tmp` which is `vscodeFileSystem` on `globalStorageUri` (slow IndexedDB-backed writes; try a memory file system for `/tmp`), clock/IO cost under `wasm-wasi-core`, or preamble rebuilds on every edit (`Built preamble Version 1 for version 7` was logged after an edit to line 8 only). Also logged on every request: `E VFS: failed to set CWD to /workspace: Link has been severed`. Repro: `vscwclang.loggingLevel: "Debug"` in user settings, open the project, read the `vscwclang` output (filter `E[`, `preamble`, `reply:`).
3. **Go to Definition into a libc++ header fails**: VS Code shows "The editor could not be opened due to an unexpected error". clangd answers `file:///sysroot/include/c%2B%2B/v1/__ostream/basic_ostream.h`, which exists only in the wasi memory file system. Needs a read-only `FileSystemProvider` (or a `vscode-vfs`-style scheme) for `/sysroot` and `/resource`, plus a `protocol2Code` mapping (`clangdClient.ts`).
4. **Tasks UI runs nothing.** `Tasks: Configure Default Build Task` lists the provider's `vscwclang: build` and `vscwclang: build (debug)` and the `vscw build` task from `tasks.json`, but `Tasks: Run Build Task` (and Ctrl+Shift+B, `Tasks: Run Task`) produce no picker, no compile lines in the `vscwclang` output, no Problems and no console error (`Tasks` output channel empty, after 25 s). The task tested: `{type: 'vscwclang', label: 'vscw build', sources: ['main.cpp'], flags: ['-Wall'], mode: 'release', group: {kind: 'build', isDefault: true}}` over a file with a deliberate error. May be a vscode.dev platform limit (no terminal for tasks) or our provider's `resolveTask`; unknown.
5. **`C_Cpp.*` fallback settings are ignored on vscode.dev.** With `C_Cpp.default.defines: ["FROM_CPPTOOLS=3"]` and `C_Cpp.default.cppStandard: "c++20"` in the workspace-file settings and `vscwclang.flags` unset, the build fails with `use of undeclared identifier 'FROM_CPPTOOLS'`: `getConfiguration('C_Cpp').get(...)` returns nothing for settings no installed extension registers. Either contribute those keys from our `package.json` (check it does not clash on desktop with cpptools) or read the raw settings through `inspect()`.
6. **Folder-level `.vscode/settings.json` is not applied for `vscwclang.flags`** when the folder is opened through this harness: the workspace is an untitled multi-root workspace, where folder settings only apply to resource-scoped settings and `vscwclang.*` are window-scoped. Unknown whether a real vscode.dev local folder also opens as multi-root (the title bar says `Workspace`, the explorer root is `Workspace > proj`); confirm with a real "Open Folder" click. If so, the settings that make sense per project should be `"scope": "resource"` and read with the folder uri.
7. **`RuntimeError: unreachable` is logged to the console by `wasm-wasi-core` (`mainWorker.js:3452`, `MainBrowserHostConnection.handleMessage`) during every build**, in a wasm function of a 87k-function module (clang; offsets `0x1a81918`), even when all steps exit 0. A failed build logs a different one (172,717-function module, `0x381209d`, then `vscwClang: build failed (exit 1)`). Probably the `proc_exit` unwind, so cosmetic, but it should be confirmed that no compile output is lost.
8. **Program traps still hang the terminal** (known, README): out-of-bounds access, divide by zero and an uncaught `throw` print only `RuntimeError: ...` / `Exception` in the browser console while the terminal stays on the last output until Ctrl+C. `try`/`catch` works with the local `v24.0.2` (eh build); the pinned `v24.0.1` still passes `-fno-exceptions` (its `compile-flags.json`), so the README line "No C++ exceptions" is right until `v24.0.2` is pinned, then it must change.
9. **Duplicate Problems**: with clangd running, `Build C++` on an erroneous file lists the same error twice, once from the build (`clang`, lower-case message) and once from clangd (`clang(init_conversion_failed)`). Consider hiding the clangd copy while a build result exists, or deduplicating by range.
10. **Smaller UX**: the terminal does not take focus after Build and Run (typing goes nowhere until a click); Debug call stack names the entry frame `__original_main` instead of `main`; the Variables pane shows `(locals not listed)` (known); step over from inside `sq` returns to the caller's loop line instead of the next line of `sq` (block-granular, known); Anycode (built in) provides inlay hints, breadcrumbs `anycode > main` and `#include` links alongside clangd, so duplicate symbol results are possible (not observed for hover/definition).
