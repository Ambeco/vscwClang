# Design: CMake, started by the extension itself

Overview: `design.md`. Back end (Ninja reader, classifier, lowering): `design_project_model.md` "Build graph". Feasibility and spike data: `build_systems_feasibility.md` (C2).

## Goal
A folder with a `CMakeLists.txt` builds, runs and debugs with no desktop-generated files: the extension runs `cmake.wasm` to configure and generate Ninja files, then the existing Ninja front end builds the result. Like Make, this is an optional layer around the core (design.md "Scope"); the core never imports it.

## Pieces
- **Pack.** `cmake.wasm` plus a trimmed `Modules/` tree (mounted read-only at `/cmake-share`) ship as their own pack with their own pin and cache folder, built by `scripts/build-cmake-wasm.mjs` (modelled on `build-make-wasm.mjs`). Separate from the toolchain so a new CMake never changes a pinned toolchain's hashes. Size is not a concern, so the pack is prefetched with the toolchain.
- **Tool guest.** CMake runs like `make.wasm`: source at `/workspace`, build dir on a writable mount, empty environment. Generated `build.ninja` files therefore hold guest paths and need no host-root rebasing.
- **Toolchain file.** Generated by the extension; wins over a project's own toolchain file (logged). Sets `CMAKE_SYSTEM_NAME WASI`, `CMAKE_{C,CXX}_COMPILER` with `_FORCED`, `_COMPILER_ID Clang`, `_COMPILER_ID_RUN`, `_COMPILER_VERSION`, `_FRONTEND_VARIANT GNU`, `_COMPILER_WORKS`, standard defaults and the per-standard compile-feature lists (names are CMake-version-specific, so they are generated when the pack is built by running desktop CMake against a logging wrapper compiler). Also `CMAKE_CROSSCOMPILING` and `CMAKE_CROSSCOMPILING_EMULATOR` set to a command the classifier maps onto the wasm runner.
- **Process layer.** CMake's process code (kwsys `RunSingleCommand`, libuv process chains) is patched to call one blocking host import, `vscw_run_process(argv, cwd, env)`. The host answers through the classify-and-map path: compilers go to `toolchain.build`, `ninja` to the graph executor, `cmake -E`/`-P` to a nested `cmake.wasm`, the emulator to the wasm runner; anything else fails with a did-you-mean. This serves `try_compile`, `check_*`, `execute_process` and `gtest_discover_tests` without a guest process model (no `fork`, pipes or `/bin/sh`).
- **Feature lists.** CMake derives `CMAKE_<LANG>_COMPILE_FEATURES` and the per-standard lists with a real `try_compile` of a feature-test source; the pack build instead preprocesses that source with the shipped clang (`-E`, no link) and writes the result into the toolchain file, so a seeded configure needs no probe for them.
- **Probe table.** Known probe results for wasm32-wasi (pthread, `<filesystem>`, warning-flag checks) are pre-seeded as a fast path, since each real probe costs a compile; unknown probes fall through to the process layer.
- **Re-configure.** Before a build, the inputs named by `build.ninja`'s re-run edge are compared with the cache; a change re-runs configure. (Ninja directories we did not generate still refuse `generator = 1` edges.)
- **UX.** `vscwclang.cmakeConfigure`/`cmakeBuild`/`cmakeRun`; settings `vscwclang.cmake.buildDir`, `.target`, `.cacheVariables`. A File API `codemodel-v2` query is written before configuring so the target picker can read the reply. `CMakePresets.json` is left to CMake (`--preset`). Default Build and Run do not look at CMake until the commands are proven.
- **Python.** `find_package(Python3)` probes by running the interpreter (six `execute_process` calls in `FindPython/Support.cmake`), and Catch2's test build requires it. The process layer answers those from a fake `python3` registered in the toolchain file (version and paths only) until a real `python.wasm` exists; anything else it is asked to run fails loudly.
- **Dependencies.** `FetchContent`/`find_package` go through a table mapping well-known names (googletest, catch2, fmt, nlohmann_json, doctest) to bundled or CORS-friendly mirrored copies; unknown ones fail loudly. Shared libraries become `STATIC` with a warning; `install` and CPack are ignored with a note.

## Build directory
`build/` in the workspace by default; `vscwclang.cmake.buildDir` (the `-B` equivalent) or a preset's `binaryDir` overrides it, and the preset wins over the default. Read-only and virtual folders use extension storage.

## Alternatives considered
### Pre-seeded cache only, no process layer
- Pros: no host import; cheapest first cut.
- Cons: every new project's probes need a hand-made table entry; `execute_process` and `gtest_discover_tests` cannot work.

### CMake subset interpreter in TypeScript
- Pros: instant start, no download.
- Cons: CMake is a large language (generator expressions, policies, modules, usage requirements); silent divergence on real projects. Kept only as the fallback if the wasm port fails.

### Consume desktop-generated `build.ninja` or File API output only
- Pros: fully faithful; already built (Ninja reader).
- Cons: needs someone to run CMake elsewhere (Linux/macOS/WSL only), which breaks the "nothing installed" north star. Stays as the back half and for other generators.

### Real guest process model (spawn hook, `/bin/sh`)
- Pros: runs any tool CMake spawns.
- Cons: much larger (pipes, shell, libc patches); one import answered by the existing classifier covers CMake's needs.

### Ship CMake in the toolchain pack
- Pros: one download.
- Cons: any CMake update changes every chunk hash and breaks installed pins; size is not the issue, versioning is.
